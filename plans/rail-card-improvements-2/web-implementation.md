## Decisions

- REQ-6's `margin-top` optical nudge isn't specified numerically by the plan ("re-tune"), so I derived it rather than guessing: the drawn glyph is the *union* of the two border strokes (not just their centerlines), and its centroid — computed analytically (border-left rect ∪ border-bottom rect, corner overlap subtracted) then rotated -45° — sits `1.4142 × v` below the box's own center, where `v` is the pre-rotation offset between the union's centroid and the box center. For the mainhead's 9×5 box (`t=1.5` border) that's `-1.485px`; for the tile footer's 7×4 box, `-1.023px`. Rounded to `-1.5px`/`-1px`. Verified two ways: (1) `getComputedStyle` in a real Playwright render confirmed `width`/`height` exactly `9×9`/`9×5` (mainhead) and `7×7`/`7×4` (tfoot) for busy/done — INV-3's computed-geometry clause holds in both hosts; (2) an 8x-device-scale screenshot of the actual cascade (`.surfseg button`'s flex `align-items:center`) showed the tick visually balanced against the busy circle's own centered line at these values (checked candidates 0/-1/-1.5/-2px before settling). Screenshots and the derivation script were scratch-only, not committed.
- REQ-1's clamp swap: verified in a real render (not just read off the stylesheet, per kb:lesson/mockup-vindicates-markup-not-cascade) with a synthetic card at 1400px — compact 81.7px (matches the plan's own Overview baseline exactly), comfortable 169.8px with `.activity` `clientHeight=47` against `scrollHeight=95` (clamp active), expanded 217.0px with `clientHeight===scrollHeight===95` (uncapped). INV-1's ordering (compact ≤ comfortable ≤ expanded) holds.
- REQ-5's margin swap: verified computed `marginTop` in the same render — `.r1` (leader) is `0px` and `.r0` (follower) is `4px`/`2px`/`4px` across comfortable/compact/expanded.
- `checkBusy`/`aria-busy` on `#update-check-button`: the plan lists `checkBusy` as a `UpdateViewModel` field but doesn't say what consumes it distinctly from `checkEnabled` (which already drives `disabled`). I used it to set `aria-busy="true"` on the button while a request is in flight, mirroring the existing `#settings-update` section's `aria-busy` pattern for apply phases (render/update.ts, `busy`/`vm.busy`) — same precedent, applied to the new control. Testable UI Elements' Name/Text Pattern for the button (`Check now`, constant) is unaffected — no label ever changes.
- `checkForUpdate`'s 200 response is decoded (needed to detect success and to satisfy the documented response shape) but its `UpdateInfo` value is intentionally *not* written into `currentUpdate` locally — `features/update.ts`'s `check()` only tracks its own request's `inFlight`/`error`. The daemon broadcasts `update` on success (protocol contract), and that broadcast — already wired via `app.on("update", ...)` — is what actually updates the rendered state, matching the existing "response carries no state, the socket does" discipline `applyUpdate`/`putPrefs` already follow (`api.ts`'s own doc comments on those). No REQ requires the optimistic path, so I kept the codebase consistent rather than introducing a second writer of `currentUpdate`.
- `checkState.error` clears at the *start* of a new `check()` call (not only on success) — REQ-12 doesn't say when a stale failure should clear, and clearing eagerly means a second press never shows a leftover reason from a prior failed attempt while the fresh request is in flight.
- All eight of this plan's web REQs (REQ-1 through REQ-6, REQ-10, REQ-11) plus the shared REQ-7/8/9/12/13 (daemon-authored fields/endpoint, consumed web-side) are implemented; none deliberately deferred.
- Every `Testable UI Elements` row in the plan's UI Specifications is implemented exactly as specified (Check-now button `#update-check-button`/"Check now"; Available readout `#update-available`; Updates status line `#update-status`; both shell indicators; `.r1`/`.r0` order; `.r3 .ctx` in every density) — none needed a substitution or was flagged unimplementable.

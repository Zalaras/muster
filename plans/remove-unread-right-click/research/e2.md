## Holds

Held as written. A live card's single-card menu offers only `Stop…`. A selection menu where every
session is live offers only `Stop…`. The cause is entirely in the client: the daemon route accepts
a live session.

## Cause

`web/src/features/railmenuitems.ts:65`. `cardMenuItems` adds `Remove` only when `!session.alive`.
That rule comes from the superseded `kb:adr/rail-card-right-click-menu-holds-session-actions`
("`Stop…` on a live session, or `Resume` … and `Remove…` on an ended one"), which in turn carried
over the old hover row that showed only on ended cards. The accepted
`kb:adr/actions-remove-allowed-on-live-session` (2026-08-27) already allows Remove on a live
session: it ends the session first and the dialog says so. The Focus header follows that ADR
(`web/src/render/mainhead.ts:136,198`: Remove is "never disabled by session state"), but the menu
never did. `selectionMenuItems` at line 90 has the same gate (Remove only when some session is
ended). The select bar's Remove button (`web/src/features/groupsselect.ts:99`) has no such gate,
and `batchPlan("remove")` keeps live ids and counts them for the "stops them first" copy. So the
menu is also out of step with the bar.

The fix: push `Remove` unconditionally in `cardMenuItems`, after the Stop/Resume primary, and
likewise in `selectionMenuItems` for any non-empty selection. `actions.dispatch("remove", id)`
already opens `removeDialogBody(session)`, which adds "This ends the session first." when the
session is alive. `removeManyBody(plan.live)` covers the batch. No protocol change, and no
stop-then-remove sequence on the client is needed.

The Focus header does not share menu code with this entry's gate. `mainhead.ts` and `focus.ts`
wire their own `#mainhead button[data-action="remove"]` straight to `actions.dispatch("remove")`.
Both paths share only the dispatcher (`web/src/features/actions.ts`) and the dialog copy
(`web/src/features/actionscopy.ts`), and neither needs editing. The menu builder
(`kb:adr/web-menu-component-single-builder`, `web/src/render/menu.ts`) does serve the
Focus-header group control, but not Stop or Remove. The sibling entry that removes the header's
Stop and Remove buttons touches `web/src/render/mainhead.ts`, `web/src/features/focus.ts` and the
markup, not `railmenuitems.ts`. So the two entries can sit in separate batches without a file
clash. Once the sibling lands, the right-click menu is the only Remove for a live session in Focus
view, which is why this entry matters.

## Questions

1. **Confirm copy for a live, working session.** Remove… already confirms, and for a live session
   the dialog adds "This ends the session first." Is that enough, or should a session mid-turn
   (working, needs input) carry a stronger warning? Recommendation: keep today's dialog, the same
   one the Focus header uses, so there is no new copy.
2. **Selection menu too?** Should the Select-mode menu offer Remove… when every selected session
   is live? The select bar already does, and its batch confirm says how many it stops first.
   Recommendation: yes, for the same rule everywhere.
3. **Item order on a live card.** Recommended: `Stop…` then `Remove…`, matching Resume, Remove… on
   an ended card.
4. **ADR.** A new ADR records that the card and selection menus offer Remove… on live sessions. It
   would supersede the menu-contents part of `kb:adr/rail-card-menu-on-selected-card-acts-on-selection`
   and cite `kb:adr/actions-remove-allowed-on-live-session`. No accepted decision is reversed; the
   developer only needs to agree to the ADR being written.

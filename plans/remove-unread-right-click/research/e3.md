The header's right cluster today, per state (`.acts` = surface switch prepended by focus.ts:110, then two buttons):
- live: `claude|shell|docs` · **Stop** (enabled iff connected) · **Remove** (danger, enabled iff connected)

## Holds

Held as written, with a scope ambiguity: "Stop" in the header is the same button that reads "Resume" on an ended
session, so "remove Stop" either removes that one button outright (Resume leaves the header too) or keeps it only for
ended sessions. No keyboard shortcut is bound to any of the three (`web/src/shortcuts.ts`, `features/shortcuts.ts`: no
hits). No focus-management code targets them beyond the native `<dialog>` returning focus to the opener.

## Cause

`web/index.html:119-122` declares the two buttons inside `#mainhead .acts`; `web/src/features/focus.ts:116-117` captures
them into `MainheadElements` (`stopResumeBtn`, `removeBtn`) and wires their clicks at `focus.ts:157-163` (dispatch
`stopResumeButton(session,true).action` / `"remove"` through the actions dispatcher); `web/src/render/mainhead.ts:20-21`
types them and `mainhead.ts:131-136,197-198` (`renderStopResume` + `removeBtn.disabled`) writes label, `data-action`,
`disabled` and hover reason every render pass. `web/src/style.css:995-998` (`.mainhead .acts .stop-resume {min-width:6ch}`)
and the comments at 900-905/982-986 size the box so the Stop↔Resume swap moves nothing. The `.acts` cluster itself
must stay: it holds the surface switch (kb:adr/focus-surface-switch-pinned-with-actions) and `fitMainheadMeta`'s
`onOneRow` measures it (`mainhead.ts:116-120`).

## Questions

1. **Resume.** The header's "Stop" is one button that reads "Resume" on an ended session. Remove it entirely (Resume
   then lives in the dead surface's endcap — shown when the claude surface is selected — and the card menu), or keep it
   as a Resume-only button on ended sessions? Keeping it reintroduces the movement the current ADR prevents (live: no
   button; ended: Resume appears) and keeps `effort-header.spec.ts`'s 16 Resume uses alive.
2. **ADR.** This reverses kb:adr/actions-mainhead-one-stop-resume-button (accepted, user-decision, 2026-10-13) and the
   "before the Stop/Resume button and Remove" sentence of kb:adr/focus-surface-switch-pinned-with-actions. OK to write a
   superseding ADR (e.g. `actions-focus-header-holds-no-actions`) that supersedes the first and restates the switch's
   right-aligned placement in the cluster?
3. **Reachability.** After removal, Stop/Remove for the focused session are on its rail card's right-click menu (live
   Remove only once sibling entry lands — this entry depends on it). The focused card is not always reachable: its group
   can be collapsed, or the filter changed after focusing, which hides it (focus resets the filter only when focus lands).
   Accept that (expand / select bar / group header Stop all… are the other routes), or should the header keep something
   (e.g. a ⋯ opening the same card menu)?
4. **Keyboard / focus.** No shortcut is bound to these buttons, so nothing to remove there. Nothing needs to receive
   focus instead (no code focuses them). Confirm no replacement keyboard route is wanted beyond the card menu's
   context-menu key / Shift+F10 on a focused card.
5. **Layout reservations.** The ended-age slot under the model and the ` (…)` width reservation exist so a Stop/Resume
   moves nothing; keep them as-is (default, harmless), or let the header reclaim that space?

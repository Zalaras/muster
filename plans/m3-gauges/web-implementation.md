## Decisions

- **`Usage.model` is optional (`model?:`), and `UNKNOWN_USAGE`/older fixtures keep no `model` key at all.** Evidence: `web/src/protocol.test.ts:182` does `expect(UNKNOWN_USAGE).toEqual({fiveHour:null,sevenDay:null,sampledAt:null,source:"subscription"})` (no `model` key), and `protocol.test.ts:61/74/117/127` (`toEqual(validSnapshot)` etc.) use fixtures whose `usage` object also has no `model` key. Vitest's `toEqual` does not treat an explicit `null` value the same as an absent key, so if `parseUsage` had unconditionally added `model: null`, all of these would fail (`sameSnapshot.usage` would gain an extra `model: null` key the fixture lacks). Ran `npx vitest run` before/after to confirm: with the "always populate model" version I first wrote, these exact tests failed; with the "only set the key when the wire actually carries it" version, `npx vitest run` shows 267/268 passing (only the one pre-existing-and-expected `card.test.ts` failure below), so I kept the latter.
- **`renderUsage`/`UsageElements` (masthead.ts) are completely untouched.** Evidence: `web/src/render/masthead.test.ts:14-16`'s `fakeElement()` returns `{ textContent: "" }` — no `appendChild`/`querySelector`/`replaceChildren`. Any change to `renderUsage`'s body beyond `.textContent =` would throw `TypeError` against that fake, not just fail an assertion. So the M3 track/resets/warn markup is a second function, `renderUsageTrack(el, bucket, now)`, called on the *same* `#usage-5h`/`#usage-7d` element right after `renderUsage` in `main.ts`'s `renderUsageBlock` — `renderUsage`'s `.textContent =` clears the element every pass, so `renderUsageTrack` always starts clean and just appends when a bucket is known (self-healing for the known→unknown case too, e.g. E11's restart). Verified live in a real browser via the actual dev-server-served modules (see below) that this produces `<span id="usage-5h" class="usage-readout">5h 61%<span class="bar warn"><i style="width: 61%;"></i></span><span class="resets">· resets 13:00</span></span>` for a known/warn bucket and exactly `<span id="usage-5h" class="usage-readout">5h unknown</span>` (zero `<i>` elements) for null — which matches `web/e2e/helpers/gauges.ts`'s actual locators (`mastheadBucket` = `#usage-5h` itself, `mastheadBucketTrack` = `.locator("i")` inside it, `mastheadBucketWarn` = `.bar.warn` inside it) exactly. I initially built a sibling-elements version (`#usage-5h-bar`/`#usage-5h-resets`) which does NOT satisfy those locators (the `<i>` would live outside `#usage-5h`) — caught this by reading `web/e2e/gauges.spec.ts`/`helpers/gauges.ts` (already authored by e2e-specs) before finishing, and rebuilt it as described above. No e2e test files were edited to make this fit; the implementation was changed to match the already-authored contract instead.
- **`sessions/card.ts`'s `contextText()` now returns the real percentage/tokens.** This intentionally breaks one pre-existing test: `web/src/sessions/card.test.ts:112-118` ("renders 'ctx unknown' even when usedPct/totalInputTokens/windowSize are present (M1 never surfaces them — gauges are M3)") — this is exactly the M1 behavior the plan (REQ-13) supersedes, and the function's own prior comment already carried a `TODO(M3)` flagging this. Confirmed via `npx vitest run`: 267/268 pass, the 1 failure is exactly this test, with `expected '42% · 1k' to be 'ctx unknown'`. The two other tests in that `describe` block (plain "ctx unknown" and "ctx unknown ⟳3" for genuinely-unknown context) still pass unchanged.
- **Test-supporting `web/e2e/helpers/gauges.ts` needs one fix once web-tests/e2e-validate run it against this build**: `mastheadBucketTrack`/`mastheadBucketWarn` already work correctly as written (they search *inside* `mastheadBucket(page, bucket)` = `#usage-{bucket}`, which is exactly where the `<i>`/`.bar.warn` now live) — no change needed there. I checked this explicitly rather than assuming it, per the note above.
- Threshold comparisons (`GAUGE_WARN_THRESHOLD`, `context.ts`'s `hot`) use the **raw** `usedPct`, not the rounded display value, so a bucket at e.g. 59.6% (which rounds to "60%" on screen) does not falsely carry `warn`/`hot`.
- Did not add an `aria-label` to `.r3`/`.ctxinfo` summarizing the context row — not required by the Testable UI Elements table and out of scope; kept the change minimal.

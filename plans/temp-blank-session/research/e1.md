# #128 — blank session when swapping sessions (research e1)

## Reproduced

Yes, with a **second musterd opened at `127.0.0.1` in the same browser**. That is how a prototype's
dashboard behaves when it is opened on `127.0.0.1` instead of `<name>.localhost`. It did **not**
reproduce under normal use. All runs used scratch daemons from the E2E harness and the
`-claude-bin` stub, with throwaway specs in `web/e2e/zz-repro-128*.spec.ts`. Those files were
deleted afterwards, and the developer's daemon and data dir were never touched.

**1. Normal use: no repro.** 8 alternating rail swaps between two sessions:
```
$ npx playwright test e2e/zz-repro-128.spec.ts --reporter=line

  1 passed (4.4s)
```
With 20 sessions, 4 of them "working" and taking status-line posts every 50 ms (far above
Claude Code's real rate, kb:fact/status-posts-arrive-in-pairs), swaps took 87–197 ms and there were no
long tasks:
```

```

**2. The prototype scenario: reproduced.** Real dashboard A has two sessions. A second musterd B
is started, and its `dashboardUrl` (on `127.0.0.1`) is opened in a second tab of the same browser
context. A is never restarted.

Control: the same run, with B opened at `diff-viewer.localhost` (what `make proto-url` prints since
02ee5da5). A is unaffected:

**3. Side finding: a slow swap under an artificial ingest flood.** This is not the reported bug.
About 500 status posts per second (each a `sessionUpsert`) saturate the browser's main thread,
because every `/ws` message runs a synchronous full `app.render()` (`web/src/wsapp.ts`). Swaps
then take 4–9 s. The daemon stays fast throughout (`/healthz` and `/api/state` answer in 5–20 ms;
`page.evaluate` takes 350–700 ms).
```
REPRO_GAP_MS=0 (2 sessions): LOAD SWAP TIMINGS 0:load-b:5318ms [evalMs=753 healthzMs=5 stateMs=7] ...
REPRO_N=20 REPRO_W=4 REPRO_GAP_MS=0: REAL TIMINGS 0:s1:9523ms(eval 662) ... posts=33848
```
Real Claude Code rates are far below this level, so it does not explain #128.

## Holds

**The cause is different from what the entry says, and the scope is narrower.** This is not a
product bug in normal use. It is a **proto-track side effect**: a prototype musterd's dashboard was
opened on `127.0.0.1`, which logged the developer's own dashboard out. The blank state outlives the
prototype because the replaced cookie stays in the browser. It is not a daemon slowdown, and not
left over in tmux, the data dir or the port.

How it matches the report:
- **Swaps go blank.** The page loaded before the clash keeps its already-open `/ws`, so no banner
  shows. Every *new* terminal socket (each swap, and each click back) is refused before the upgrade
  with a 401. Each one shows the scrim overlay "disconnected — daemon down" over an empty pane.
- **"Daemon down" while the prototype runs.** When `/ws` reconnects, it also gets a 401, so the
  banner reports the daemon as down.
- **A refresh shows nothing for a while.** `/` returns 401 with the "Muster is not running here"
  page until the dashboard is opened through its token URL again (`make run`/`-open`, or
  `tokens.json`'s `dashboardUrl`).
- **It persists after the prototype stops.** Stopping B does not restore A's cookie, and the
  dashboard never re-authenticates by itself.
- **It does not happen on the other computer.** That machine ran no prototype.

What the prototype shares with the real musterd, checked one item at a time:
- **Port:** not shared. It is derived from the name: diff-viewer → 28820, better-terminal → 29642.
- **Data dir:** not shared (`.proto-data`).
- **tmux socket:** not shared (`-tmux-socket muster-proto-<name>`).
- **Vite proxy:** none.
- **localStorage:** not shared, because it is per origin, including the port.
- **Shared: the `muster_auth` cookie.** A cookie is scoped to the host and ignores the port, so any
  two musterds opened on `127.0.0.1` overwrite each other's cookie.

Both proto worktrees exist (`../muster-proto-diff-viewer`, `../muster-proto-better-terminal`), both
at 02ee5da5, so they have the `<name>.localhost` fix. The diff-viewer prototype ran round 1 on
2026-11-19, the day the issue was filed.

**Was "daemon down while a proto runs" meant to be fixed already?** Yes: 02ee5da5 (2026-11-17,
`docs(pipeline): prototypes run beside each other and the developer's Muster — a port pair from the
name and a dashboard at <name>.localhost`). The fix only works if the prototype is opened at the
URL `make proto-url` prints. `make proto-run` still runs musterd in the background, and musterd
still logs `dashboard_url=http://127.0.0.1:<port>/auth?token=…` at startup. That log line, or
`.proto-data/tokens.json`, is the easy way to open it on `127.0.0.1` anyway, and with it the
clash returns. Which URL was actually opened on 2026-11-19 cannot be read back from the repo.

## Cause

`internal/server/auth.go:72-79`: `handleAuth` sets the host-scoped cookie `muster_auth` (no port in
its name; kb:anchor/transport in `docs/protocol.md:48` specifies exactly this). Every musterd on
`127.0.0.1` therefore writes the same browser cookie, and the last `/auth` wins. After that,
`requireCookie` (`internal/server/auth.go:45-53`) answers 401 to the other daemon's `/ws`,
`/ws/terminal/{id}` and `/`.

On the web side, `web/src/terminal/pane.ts:224-228` and `web/src/terminal/overlay.ts:9-13` map the
refused upgrade (close 1006) to "disconnected — daemon down". No code in `web/src` tells a 401 apart
from a dead daemon (`grep -rn 401 web/src` finds nothing), and none sends the developer back to
`/auth`. So the logged-out state shows up as blank, "daemon down" panes on every swap, and it lasts
until the developer reopens the token URL by hand.

## Proof

- **Option C** (E2E, journey across two live daemons; e2e-specs writes it). In `web/e2e/auth.spec.ts`,
  add a test such as "a second musterd authed on the same host leaves the first dashboard's
  terminals attached". It starts a second daemon with `startDaemon()`, opens its `dashboardUrl` in a
  second page of the same context, then clicks a rail card on the first. Failing assertion today:
  `expect(terminalRegion(page, "real-a")).toContainText("MUSTER-STUB-READY")` times out, because the
  region shows "disconnected — daemon down". This is exactly `zz-repro-128c` above. A daemon unit test
  (daemon-tests, `internal/server/auth_test.go`) could also assert that the cookie name includes the
  listen port.
- **Option B** (E2E, same setup; e2e-specs). Failing assertion today:
  `expect(terminalOverlay(region)).toHaveText(/relaunch|signed out/)`. It receives "disconnected —
  daemon down". A web unit test (web-tests) for the 401-vs-unreachable classification.
- **Option A:** no product test. `make hooks-test` only covers the feedback receiver.

## Questions

1. **Which outcome?** Close as fixed by 02ee5da5. Or harden the tooling (A), so `make proto-run`
   never shows the `127.0.0.1` URL. Or a product fix: B (say "signed out — reopen the dashboard
   link" instead of "daemon down"), C (per-port cookie name, a protocol change), or both. B also
   covers any other way of losing the cookie. C removes the clash for anyone running two musterds,
   e.g. `make run` beside the installed one.
2. **If C:** renaming the cookie logs out every open dashboard once on upgrade. The update restart
   reloads the page (kb:adr/update-restart-reloads-dashboard) and would land on the 401 relaunch
   page. Is that acceptable, or should the daemon also accept the old name during a transition?
3. Should the flood finding (one synchronous full render per `/ws` message; main thread saturates
   at hundreds of upserts per second) be filed as its own perf tweak (coalesce renders to one per
   animation frame)? It is not #128's cause, and it sits well above real Claude Code rates.

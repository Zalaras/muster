## Holds

**It held, but the cause is different from the one the entry implies.** Saving and reading the
port both work. When `y` is answered, the file is written and the next plain start binds the
saved port. Nothing reads the port file late or from the wrong place, and the data dir is
correct. What fails is the prompt itself:
- It is printed and then at once buried by log lines from goroutines that start after serving:
  the Claude version check, the usage poll and the update/unmanaged-install notice. The cursor ends up after
  a log line, and nothing marks it as a question that is still waiting.
- If the daemon shuts down (Ctrl-C) before the prompt is answered, it counts as **No** and nothing is printed.
  The developer is not told that the port was not saved.

Running `--port 8766` twice gives the same result both times. The real data dir on this Mac
(`~/Library/Application Support/Muster`) has no `port` file, which fits this (read-only `ls`).
Note: the report came from the laptop, not this Mac.

## Cause

`cmd/musterd/main.go:299` (`maybeOfferSavePort`) starts the prompt on its own goroutine. It
runs after `srv.Start()` (`main.go:281`) and `logStartup` (`main.go:289`). By then the
version-watch, usage-poll and update-check goroutines are already writing zerolog lines to the
same stderr. So `Save port N for future starts? [y/N] ` (`cmd/musterd/port.go:126`, printed
by `lineInput.confirm`, `cmd/musterd/stdin.go:61`) is followed straight away by unrelated log
lines, and nothing prints it again. On shutdown, `stopSavePrompt()` (`main.go:323` → `port.go:117-120`) cancels
the read. `confirm` then prints only a bare newline (`stdin.go:63-65`), and `offerSavePort`
returns with no log line (`port.go:126-128`). An unanswered prompt is a silent No. This
matches kb:adr/connection-port-saved-per-profile-on-prompt ("default No"; "The daemon serves
while the prompt waits"), so the code does what the ADR says. The UX makes the question easy
to miss and gives no feedback when it lapses.

## Route

`fix`. This is a daemon-only CLI UX change with no protocol, UI surface or feature-spec change,
unless the developer picks an option that supersedes the ADR. That would be one new ADR on the same small track.

## Questions

1. **What should the fix be?** The save path works, and "unanswered = No" is what
   kb:adr/connection-port-saved-per-profile-on-prompt says. The choices are:
   (a) keep the async prompt, but print it again once the startup log lines have passed, and on
   shutdown log "port N not saved; answer y at the prompt next time" if it was never answered.
   This keeps the ADR.
   (b) ask synchronously before serving or before the async checks start, so the prompt is the last line
   and the daemon waits for the answer. This supersedes the ADR's "serves while the prompt waits".
   (c) save a flag-given port without asking. This supersedes the ADR's option D.
   (a) is the smallest change and keeps every accepted decision.
2. On the laptop, something else already holds 8765 (another profile or a stale musterd).
   With the save working, that is expected and needs no change. Confirm the entry is only about the
   prompt, not a request to fall back to a free port (the ADR rejects fallback).

## Answers

Developer, 2026-11-06, verbatim: "2b"

Resolved: option (b) — when a port is given with `-port N` and differs from the saved/default port,
musterd asks "Save port N for future starts? [y/N]" **before** it starts serving and waits for the
answer, so no startup log line can bury the question; default stays No. Carries a new ADR
superseding the "serves while the prompt waits" part of
`kb:adr/connection-port-saved-per-profile-on-prompt` (the opt-in save and default No stand). With no
terminal on stdin there is nothing to wait for: behave as today's non-interactive path. Question 2
(automatic fallback to a free port) was not asked for: by choosing (b) the developer scoped the
entry to the prompt only; no port fallback (the ADR's rejection of it stands).

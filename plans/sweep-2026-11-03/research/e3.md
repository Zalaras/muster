What the replay shows:

- **The `Stop` drops the card to `idle`** while 2 subagents are still running. The card's bottom line reads `2 background tasks`.

## Holds

**Held, with a different scope.** The symptom is real: a plan-mode session whose main turn ended with subagents still in the background reads `idle`. But it is not a planning-specific defect, and the code is doing what the accepted decisions say.

- **What "planning" is.** "planning" is not a separate attribute that Stop wipes. It is one of the six displayed states: `StatePlanning`, `internal/session/session.go:19`, spec `docs/features/lifecycle/spec.md:23`, "mid-turn with the permission-mode latch on `plan`". It is the plan-mode spelling of `working`: `activeState()`, `internal/session/session.go:333-338`.
- **What Stop does to plan mode.** The plan-mode latch (`PermissionMode`) survives Stop untouched. Stop even re-latches it from its own `permission_mode`. What Stop does is end the turn, so the state goes from active to `idle`.
- **The same question as #96.** #110 is the subagent case of #96: should a session with background work still running read as working (in plan mode, `planning`), or as idle? The accepted decision kb:adr/lifecycle-background-tasks-count-not-state says idle plus a count. It considered and rejected option C, "`working` while subagents run". kb:adr/lifecycle-subagent-marked-events-not-stragglers (superseded, but its Consequences carried forward) explicitly accepted "a Stop with background work still running lands idle and the first marked hook returns the session to working, a brief blip". Fixing #110 as asked means reversing that ADR.

There is no narrower bug that holds on its own. A plan-mode-only fix, keeping `planning` past Stop when the latch reads `plan`, would mean:

- an idle plan-mode session could never read idle;
- `idle` would be redefined for one mode only.

## Cause

`internal/session/machine.go:217-238`, `applyTurnClosed`. A main-agent `Stop` closes the prompt and records `input.BackgroundTasks` as a count (`:231-233`). It then calls `endTurnIntoIdle` unconditionally; the only exception is a subagent's permission wait (`:237`).

The count is never a state input, by kb:adr/lifecycle-background-tasks-count-not-state. So the card lands `idle` even while `Stop.background_tasks` lists running subagents.

Subagent-marked tool hooks then move it back to `activeState()` (`machine.go:29-60`), which is `planning` because the latch is still `plan` (`session.go:333-338`). Two things put it back to `idle`:

- a gap between those hooks;
- the `idle_prompt` that ends a fresh-prompt-id subagent stretch (`applyIdleNotice`, `machine.go:255-268`, per kb:adr/lifecycle-idle-prompt-ends-turn-never-attention).

The interpreter is not at fault. `interpretStop` (`internal/claudecode/interpret.go:184-203`) already counts running tasks of every type, subagent and shell alike.

## Holds

**It holds, with a wider cause than the entry gives, and the cause is a rule as designed.**

- **Path 1 (leave):** the three sessions do come back on the first start, as ended resumable rows.
  The next start deletes them. That is exactly e1's defect.
- **Path 2 (kill, or `y` at the prompt):** the rows are already `alive=0` when musterd exits. The
  **very first** start deletes them, so they never come back at all. `web/e2e/reconcile.spec.ts`
  E4 (:115) asserts this today.

The issue's "0 sessions" snapshot fits either path. Whether the sessions were killed at shutdown or
separately makes no difference: what deletes the rows is the reconcile sweep.

**Does the e1 fix alone resolve #47?** That depends on which e1 option is chosen:

- **e1 option A** (reconcile never deletes, rows are kept until Remove): this resolves both paths.
  Nothing more is needed.
- **e1 option B** (sweep only rows the user ended, keep crash or pane-death rows): this resolves
  path 1 only. A row ended by `-on-exit kill` or `y` counts as user-ended and is still swept at the
  first start, so #47 stays broken on path 2. #47 then needs the kill-at-shutdown end cause to count
  as "keep" as well.
- **e1 option C** (age-based sweep): this resolves both paths, but only for rows younger than N.

So #47 is the same seam as e1, but it is a superset of it. e1's wording ("survive only one start")
describes path 1, and #47 also covers path 2, where rows survive zero starts. They should land as
one batch with one ADR.

## Cause

`internal/session/reconcile.go:123-127` (`classifySessionsByOwnership`) checks each row whose
`muster-<id>` is absent from the socket:

- if the row has `alive=true`, it goes to `toEnd`, and `markEnded` (`internal/session/liveness.go:235`)
  stamps it ended and keeps it;
- if the row has `alive=false`, it goes to `toSweep`, and `actOnReconcile` (`reconcile.go:87-96`)
  deletes it with `removeSessionRecord(ctx, id, false)`.

The rule is documented at `reconcile.go:31-34`. On path 1, start #1 turns `alive=1` into `alive=0`
and start #2 sweeps the row. On path 2, `shutdownGracefully` → `srv.EndAllSessions` → `Manager.EndAll`
(`cmd/musterd/onexit.go:65-70`, `internal/server/server.go:292`) writes `alive=0` before exit, so
start #1 sweeps the row. Nothing persists *why* a row ended, so reconcile cannot tell a crash from an
End or a kill.

This is the designed rule:

- kb:adr/lifecycle-ended-rows-swept-next-start (option C, "every death gets one resume chance",
  user-decided) is superseded;
- its rule is restated unchanged by the **accepted** kb:adr/lifecycle-reconcile-converges-with-the-socket
  ("A row whose `muster-<id>` is absent follows the superseded rules exactly");
- kb:adr/lifecycle-shutdown-leaves-sessions-running's kill consequence assumes the sweep;
- `docs/protocol.md:1893-1898` and `:1914-1916` ("so the next startup sweeps it") say the same.

`go tool kb for internal/session/reconcile.go` does **not** surface these ADRs, because their
`files:` name `internal/session/manager.go`. A fix should repoint the new ADR's `files:` at
`reconcile.go`.

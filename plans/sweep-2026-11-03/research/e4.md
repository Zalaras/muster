## Holds

Holds as written. After the keyboard Dismiss, focus is on `<body>`, not in the terminal and not on any header control. The same thing happens whenever the strip hides while its Dismiss has focus. Today the only route there is a successful Dismiss. A failed Dismiss (daemon down, 500, abort) leaves the strip shown, so focus stays on the button. That path is already correct and must stay that way.

## Cause

`web/src/features/focus.ts:166-171` wires Dismiss to `deps.effort.dismiss(id)` (`web/src/features/effort.ts:13-17`), which sends the DELETE and does nothing with focus. The strip only hides later. The `sessionUpsert` with `effortWarning: null` triggers a render, `renderView` → `renderMainhead` (`web/src/features/focus.ts:266`) → `renderEffortStrip` (`web/src/render/effortstrip.ts:21`) sets `strip.hidden = true`, and Chrome's focus fixup drops the focused Dismiss to `<body>`. No code on that path checks where focus was. The precedent is the notes panel's `close()` (`web/src/features/notes.ts:203,212-214`). It records `hadFocus` before it removes its own UI and then sends focus to `surfaces.focusSelected(id)`. If that leaves focus on `<body>` (Docs selected, ended session), it falls back to a header control (the glyph). The notes spec states this rule: "returns focus to the selected terminal, or to the glyph when none shows" (`docs/features/notes/spec.md:41`).

**Proposed fix (reuse the notes pattern):** in `renderView`, record `const hadFocus = mainheadElements.effortStrip.contains(document.activeElement)` before `renderMainhead`. After it, if `hadFocus && mainheadElements.effortStrip.hidden`, call `deps.getSurfaces().focusSelected(session.id)`. If `document.activeElement` is still `null` or `body` after that (Docs selected, ended session, no session), focus the header's always-visible Session actions `⋯` (`moreBtn`, already held at `focus.ts:155`; kb:adr/focus-header-holds-switch-and-session-menu). Putting the check at hide time rather than in the click handler means:

- the failure path, where the strip stays, keeps focus on Dismiss;
- a window whose Dismiss lost focus to another window's dismissal is covered too;
- `effort.ts` stays a thin API caller.

## Questions

1. **Where focus lands.** The entry says "somewhere sensible in the header". The established pattern for the Focus header puts focus back in the selected terminal: the notes panel's close (`docs/features/notes/spec.md:41`), and kb:adr/focus-rail-click-focuses-terminal for the rail. It falls back to a header control only when no terminal shows.
   - **Recommended:** terminal first, then the Session actions `⋯` when Docs is selected or the session has ended. A keyboard user who dismissed a warning most likely wants to go back to typing.
   - **The alternative the entry's wording suggests:** always the header's `⋯`, which is predictable and always visible.
   
   The effort readout the warning is about (`.model .eff`) is a non-focusable span, so it cannot be the target unless it gains a tabindex. That is not recommended.

## Answers

Developer, 2026-11-03, verbatim: "4. Your recommendation"

Focus goes to the selected session's terminal (surfaces.focusSelected), falling back to the header's Session actions ⋯ when no terminal shows (Docs selected, ended session). Only when the strip had focus as it hides; a failed Dismiss leaves focus on the button.

## Decisions

- Fake "musterd" script had to be `exec sleep 3600`, not `while true; do sleep 3600; done` — the latter forks a `sleep` child of the shell; SIGTERM to the shell (the direct child Node tracks) kills the shell but leaves the forked `sleep` as an orphan still holding the inherited stdout/stderr pipe open, which hangs the check script itself forever (measured: `time (npm run -s e2e:fixture-leak-check)` ran past a 60s and then a 120s timeout with the fix absent, printing nothing further after the tmpdir-leak line). `exec` replaces the shell's own process image (same pid, no descendant), matching `validation.md`'s own manual repro shape (`bin/musterd` swapped for `exec sleep 600`) — after switching, the same run completed in ~10.5s.
- Process-survival check uses a pidfile the fake script writes with `$$` before `exec`, not `pgrep -f <fakeBinPath>`. Measured: after `exec sleep 3600` replaces the process image, `ps`/`pgrep -f` no longer sees `fakeBinPath` in argv at all (execve replaced argv with `sleep 3600`), so `pgrep -f fakeBinPath` always returned 0 matches even when the process was genuinely alive and leaked — a silent false negative. Reading the pid from a file written before the `exec` (same pid persists across `exec`, only the image changes) correctly detected the leak: reverting the REQ-4 guard and rerunning printed `fake-musterd (pid <n>) survived start()'s rejection`.
- The self-test calls `process.exit(code)` explicitly at the end rather than letting Node drain naturally. Measured: with the REQ-4 guard reverted, the run detected and reported both the surviving pid and the leaked tmpdir, then still hung past a 60s timeout — the guard-less path also leaves the deny-stub's HTTP listener open (which this script can't reach to close itself, since a failed `start()` returns no daemon handle to a caller), and that live listener is exactly the kind of open handle that stops Node's event loop from ever draining. `process.exit()` guarantees the check reports non-zero instead of hanging; console output writes to a pipe are synchronous on POSIX so nothing is lost. With the guard restored (nothing left open), behaviour is unchanged — same clean exit 0 in ~10.5s.
- W3 discrimination proved directly, not asserted: ran the self-test three ways — (1) guard in place: `exit=0` in ~10.5s, "clean" printed; (2) guard reverted (`start()` back to its pre-fix flat sequence, no try/catch): `exit=1` in ~10.5s, printing the surviving pid and the leaked tmpdir; (3) guard restored again: back to `exit=0`. Reversion was done in-place on `web/e2e/helpers/daemon.ts` and restored from a saved copy afterward — the shipped file is the guarded version.
- `web/scripts/e2e-fixture-leak-check.mjs` was written as `.mjs`, not `.ts`, following `contrast.mjs`'s existing precedent (the only other script under `web/scripts/`) — plain Node ESM needs no `tsconfig.json` include change, no `allowImportingTsExtensions`, and stays consistent with the one other non-Playwright script in the directory. It imports `../e2e/helpers/daemon.ts` with an explicit `.ts` extension, which Node's native (unflagged) type-stripping on Node 24 resolves directly — verified (`node scripts/e2e-fixture-leak-check.mjs` runs without any transpile step).
- `serveEmbedded`'s `copyFile(musterdBin, daemon.embeddedBinPath)` still reads from the module-level `musterdBin` constant, not `resolvedMusterdBin` — REQ-12's override is scoped to "the binary to spawn" for the ordinary (non-embedded) path only; no test seam in this plan combines `musterdBinOverride` with `serveEmbedded`, and the embed-dashboard fixture's whole point is proving the checked-in binary serves its own embedded assets, which an override would defeat.

## Holds

Holds as written, with a slightly wider scope: the same reducer path also hits `select('shell')`
(`POST …/shell`, which starts terminal 1 when none runs). There a stale `[]` sends the window back to
`claude`, and the following `[1]` does not bring `shell` back. The later list never restores the
window in either case.

Daemon side, which shows the ordering is real: `spawnInSession` (`internal/server/shells.go:136`)
calls `f.changed(ctx)` → `poller.sync` → `tick`, which broadcasts the post-spawn list into every WS
outbox **before** `writeJSON` sends the 201/200. A tick already running when the spawn started holds
`tickMu`, so its pre-spawn list (`shellactivity.go:112-135`, `reconcile` 156-170) goes into the
outbox first. The WS outbox is written by its own goroutine, and the HTTP reply travels on a
different connection. So the browser can resolve the fetch before it handles the stale list, and
then the post-spawn list. Any list sent just before the spawn (for example a busy flip) has the same
effect. No E2E reproduction: the window is milliseconds wide.

## Cause

`web/src/features/surfaces.ts:127-130` (`applyTerminalList`) passes every `terminals` message
straight to `terminalsChanged` (`web/src/terminal/surfaceswitch.ts:54-69`). That reducer reads any
list that lacks the shown `n` as "the shown terminal ended". It falls back to the lowest `n`, or to
`claude` when the list is empty, which is the fallback in kb:adr/surfaces-last-shown-terminal-per-window.
`showAndSelect` (`surfaces.ts:155-161`, reached from `newTerminal` at 197-206 and from `select` at
194) sets `shell = n` from the HTTP reply, but nothing records that this `n` has not yet been
confirmed by any list. A list the daemon sent before the spawn therefore reads as the new terminal's
exit. The next list does contain `n`, but the reducer keeps whatever is shown when that terminal is
in the list (line 60), so the switch is never undone.

## Route

`fix`. A client-only fix exists, and the protocol does not change. The ordering it relies on is
already true: the daemon queues the post-spawn list on `/ws` before it writes the HTTP reply. A
list version or `seq` on `terminals` would be the protocol-level fix (not-small-track: protocol),
but it is not needed.

## Questions

1. **What if the spawned terminal never shows up in a list?** If it exits before the daemon's
   post-spawn poll, no list will ever include it. A plain "hold until listed" would then keep the
   window on a dead terminal (attach returns 409 `no_shell`). Options:
   (a) end the hold after a short time (~2 s, in line with REQ-6's ~2 s), then apply the latest list
   as normal (recommended);
   (b) accept the edge, since the entry only asks for "stays shown until a list that includes it
   arrives".
2. **Scope: should the `select('shell')` path be covered too?** It has the same race (stale `[]`
   sends the window back to `claude`), and the expected behaviour as written ("a terminal the window
   asked for") already covers it. Recommended: yes, one fix for both.

## Recommended fix (plain words)

When the window shows a terminal because of its own spawn reply (`newTerminal`, or `select('shell')`
after `POST …/shell`), remember that number per session as "pending". While it is pending, a
`terminals` message still updates the list, count and busy indicator, but it does not move the
window off the pending terminal and does not drop `shell` back to `claude`. The pending mark clears
on the first list that includes the terminal; after that the normal last-shown/lowest fallback
applies. It also clears on a short timeout, which then re-applies the latest list (question 1), and
whenever the session's selection changes (for example a newer select, or `sessionRemoved`/snapshot
clearing the state). This is client-only, in `features/surfaces.ts`. The pending set can live beside
`selectRequestId`, or as an optional `pending` argument to `terminalsChanged`.

Recorded with it (orchestrator):
- **Fix: C.** The contract is already committed on `main` before this sweep, by the developer's
  instruction: `kb:adr/surfaces-terminals-list-revision` and `docs/protocol.md`
  (`kb:anchor/ws.shell-activity` — `rev` on `terminals`; `kb:anchor/ws.snapshot` —
  `terminalsRev`; `kb:anchor/sessions.shell` § Revisions — `rev` on all four terminal routes'
  replies, `DELETE` now `200 {rev}`). The batch **implements that contract exactly** on both
  sides; it does not change it. If the contract proves wrong or unimplementable, fail with the
  question rather than editing `docs/protocol.md`.
- **Daemon:** one counter in the shell-activity poller, bumped per broadcast under `tickMu` so
  revs leave in order; the poller remembers each session's latest broadcast rev (kept after its
  list goes empty); `Current()` returns lists and `terminalsRev` consistently; each terminal
  route reads the session's rev after its `changed` sync and puts it in the reply.
- **Web:** per-session highest-seen rev, raised by `terminals` messages, by the four replies and
  by the snapshot (which sets every session); a `terminals` message below it is ignored (equal
  applies). On a spawn reply (`newTerminal`, `select('shell')`) whose rev is at or below the
  seen rev while the current list lacks its `n`, the terminal already ended: do not show it,
  the normal fallback applies.
- Old questions 1 and 2 are moot: no hold and no timeout; the `select('shell')` path is covered.
- **Proofs:** the web unit tests in § Proof (stale list after `newTerminal`'s reply keeps 2
  shown; stale `[]` after `select('shell')`'s reply keeps shell 1), plus a stale-list-after-close
  case and a stale-list-after-rename case, plus "reply rev at or below seen and n missing → not
  shown". Daemon unit tests: revs strictly increase across broadcasts; each route's reply `rev`
  equals the session's latest broadcast rev; `DELETE` answers 200 with `rev`; snapshot carries
  `terminalsRev`. Render fixtures regenerate for the new snapshot key.
- Scope note from reading `internal/server/shellactivity.go`: the poller broadcasts only a list
  that differs from the previous one, so in practice the stale list needs another change in the
  same tick. Unit level is right; no E2E for a millisecond race.

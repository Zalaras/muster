An earlier run gave the teammate agent_id-marked PreToolUse/PostToolUse. There the subagent activity had already moved the card to `working`, and the closed-prompt main PermissionRequest was dropped (`state = working, want needs_input`). That is the #123 symptom from the same root.

## Holds

It holds as written. One scope detail: in a hook payload PreToolUse, PostToolUse and PostToolBatch are the same `StateInput` (`KindTurnActivity`). So "reopen on PreToolUse only" needs the interpreter to pass a new neutral signal across the package boundary.

## Cause

`internal/session/machine.go:33-36`: `closed := promptID != nil && sess.promptClosed(*promptID); if closed && !input.FromSubagent { return false }`. It drops every main-agent turn-activity on a closed prompt. `machine.go:67-68` does the same for `KindNeedsInputPermission`. A teammate re-invocation reuses the prompt_id that its own Stop closed (`applyTurnClosed`, `machine.go:222-226`, via `closePrompt`, `internal/session/session.go:305`). It also has no UserPromptSubmit. So every main-agent hook of the new turn reaches these guards and changes nothing, and the card stays `idle` while the main agent works. The guard cannot tell PreToolUse from PostToolUse. `internal/claudecode/interpret.go:149-155` maps `"PreToolUse", "PostToolUse", "PostToolBatch"` to one identical `StateInput{Kind: KindTurnActivity, …}`.

The fix:
- **Interpret.** `interpret.go` gives PreToolUse and PermissionRequest a neutral flag, for example `StateInput.OpensTurn bool`. The name is a choice, and no Claude Code vocabulary goes into `internal/session`.
- **Reopen helper.** `session.go` gets a `reopenPrompt(id)` that removes the id from `closedPromptIDs`.
- **Both guards.** They become `closed && !input.FromSubagent && !input.OpensTurn`. When the flag is set, they reopen the id and adopt it as current.

The id must leave the ring, not only become `currentPromptID`. Otherwise the re-invocation's second Stop reaches `closePrompt`, which returns early because `promptClosed` is true and so never clears `currentPromptID`.

The `<agent-message` skip goes in `interpret.go:146`, the same `strings.HasPrefix(*f.Prompt, backgroundCompletionTag)` test that `const backgroundCompletionTag` at `interpret.go:11` feeds. It needs a second prefix constant. It touches no other file.

## Questions

1. **Protocol and spec prose.** The `kb:anchor/state.transitions` table and `kb:anchor/state.ordering` rule 2 in `docs/protocol.md` say an unmarked closed-prompt event "never reopens a turn". That text must change, as must the `<task-notification>`-only `lastPrompt` clause and the lifecycle spec's "Ordering and loss" paragraph. Is doc-reconcile, inside /fix, editing the protocol state table acceptable for this item, given the "nobody changes the protocol unilaterally" boundary? No wire shape changes.
2. **Which closes it covers.** Should reopening apply to a prompt closed by any closer (StopFailure, idle_prompt, transcript interrupt, compaction end) or only by Stop? The decision says "closed prompt", so all closers are covered. A late PreToolUse after an interrupt would then also reopen. This falls inside the accepted curl-timeout edge case, but the new ADR should say so explicitly.
3. **Subagent-owned permission wait.** The case is a main PreToolUse on a closed prompt while a subagent owns a permission wait. With the guard placed before `permissionWaitOwnedByOther`, the main PreToolUse reopens and adopts the prompt but keeps `needs_input` (INV-B). This seems right, but the new ADR should state it.
4. **Comment and invariant prose.** These say a closed prompt is "never reopened": the INV-P comments in `machine_test.go` (lines 438-474 and 605-672), the guard comment in `machine.go:37-41`, and `kb:adr/lifecycle-subagent-marked-events-not-stragglers`, whose wording covers marked events only and still holds. The test comments need narrowing to "unflagged/unmarked". This is mechanical, not a decision.

## Answers

Invocation (verbatim): "Go, one batch. Root cause is kb:fact/teammate-reinvocation-reuses-closed-prompt-id: when a teammate finishes, Claude Code re-invokes the main agent with no UserPromptSubmit, under the prompt_id that its own Stop already closed. Every other main-agent event on a closed prompt stays inert as today, PostToolUse and PostToolBatch included, because those are not awaited and can genuinely straggle. Basis: Claude Code waits for PreToolUse and PermissionRequest (kb:fact/hook-await-per-event), and the hook only returns once ingest has enqueued the event. So an earlier turn's PreToolUse is always queued before that turn's Stop. Write a superseding ADR for the "a closed prompt never reopens" part of kb:adr/lifecycle-prompt-ordering-guards. Record this edge case in the ADR: if ingest is slow enough that curl's 2 s --max-time fires, that ordering guarantee is gone. A late PreToolUse could then reopen a finished turn and show WORKING until the next Stop or idle_prompt corrects it. Accepted, not guarded against. Same batch: skip a UserPromptSubmit whose prompt begins <agent-message as a "last prompt", the same way <task-notification> is skipped. Tests: unit tests that replay the two captured sequences from the fact. #122: main tools after the Stop must show working. #123: AskUserQuestion in the re-invoked turn must show needs_input while a teammate's agent_id-marked hooks keep arriving.

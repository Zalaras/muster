## Holds

The developer's diagnosis holds as written. The fix touches one extra thing:

- **Teammate traffic after the reopen does not knock `needs_input` back to `working`.** No extra fix is needed. A main-agent PermissionRequest records `AttentionAgent = ""` (main). A teammate's marked hook carries `Agent = "t1"`, so `permissionWaitOwnedByOther` returns true and the activity arm returns early (INV-B, kb:adr/lifecycle-attention-owned-by-raising-agent). The reopen replay above shows this.
- **Reopening must take the id out of the `closedPromptIDs` ring.** Setting `currentPromptID` alone is not enough. Otherwise the main PostToolUse that follows the answer is still "closed and unmarked", so it stays inert and the session stays `needs_input` until the second Stop. The second Stop's `closePrompt` would also return early, because the id is "already closed", and leave `currentPromptID = p1` behind. A `reopenPrompt(id)` helper in `session.go` is needed, the counterpart of `closePrompt`.
- **`StateInput` cannot tell main PreToolUse apart from PostToolUse, PostToolBatch or UserPromptSubmit.** All four map to `KindTurnActivity`. So `Interpret` must pass along a new neutral flag, for example `ReopensClosedPrompt bool`, set only for a main-agent (no `agent_id`) `PreToolUse` and `PermissionRequest`. The PermissionRequest case could be told apart without the flag (`!FromSubagent && !AgentUnknown`). Using the same explicit flag for both keeps the existing row `closed_prompt_unmarked_permission` in `TestApplyInput_CrossStateInvariants` valid: it builds a bare `StateInput{Kind: KindNeedsInputPermission}`, which should stay inert. A `Notification{permission_prompt}` stays inert on a closed prompt, as decided. In practice it arrives about 6 s after the PreToolUse has already reopened the prompt (kb:fact/ask-user-question-hook-sequence).
- Shared item for #122/#123: `interpret.go` only skips the `<task-notification>` prefix (`backgroundCompletionTag`, `interpret.go:11`, applied at about `:152`). It needs a second prefix, `<agent-message`. Per the fact, that UserPromptSubmit arrives on an open or a new prompt_id, so it already transitions. Only `LastPrompt` is wrong today.

## Cause

`internal/session/machine.go:33-36`, plus `machine.go:67-69` for the permission arm. Both the `KindTurnActivity` and the `KindNeedsInputPermission` arm return early when `promptID` is in `closedPromptIDs` and the input is not `FromSubagent`. That is kb:adr/lifecycle-prompt-ordering-guards' "a closed prompt never reopens". Claude Code 2.1.322 re-invokes the main agent after a teammate finishes, with no UserPromptSubmit, and reuses the `prompt_id` that its own Stop just closed (kb:fact/teammate-reinvocation-reuses-closed-prompt-id). As a result, the re-invoked turn's main PreToolUse(AskUserQuestion), PermissionRequest and permission_prompt all hit the guard and are dropped. Marked teammate hooks on that same closed id do get through (`machine.go:37-41`, kb:adr/lifecycle-subagent-marked-events-not-stragglers), and each one sets the state to `working`. `interpret.go:155-161` and `:165-171` give main PreToolUse and PermissionRequest no marker that would let the machine treat them differently from a PostToolUse straggler. PostToolUse really can arrive late, because it is not awaited. PreToolUse and PermissionRequest cannot arrive after the Stop, because PreToolUse is awaited (kb:fact/hook-await-per-event).

Record this edge case in the ADR: if ingest is slow enough that curl's 2 s --max-time fires, that ordering guarantee is gone. A late PreToolUse could then reopen a finished turn and show WORKING until the next Stop or idle_prompt corrects it. Accepted, not guarded against. Same batch: skip a UserPromptSubmit whose prompt begins <agent-message as a "last prompt", the same way <task-notification> is skipped. Tests: unit tests that replay the two captured sequences from the fact. #122: main tools after the Stop must show working. #123: AskUserQuestion in the re-invoked turn must show needs_input while a teammate's agent_id-marked hooks keep arriving.

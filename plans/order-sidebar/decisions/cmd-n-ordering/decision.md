**Outcome**: A — ⌘N follows the rail: `focusNth` uses `orderRail(store.values(), railSort)`, so ⌘1–9 selects the nth card in the order the rail currently displays (manual or attention mode). Costs the one-key jump to the most-blocked session.
**Reached by**: consensus (advocate-b conceded in turn 3)
**Decisive argument**: E7 (`web/e2e/views.spec.ts:69`, "Cmd+1 focuses the top-priority session regardless of launch order") was advocate-b's only evidence that the attention reading of ⌘N was *chosen* rather than inherited from the rail and the shortcut being one sort function. advocate-a showed it records no decision between the attention order and a user-authored rail order — no user-authored order existed at M1; it discriminates only against store-insertion order — and that it falls in the repair class the pipeline already applied to three `actions.spec.ts` tests (test-specs.md Repairs #3–#5: select Attention mode before the priority assertion, assertion preserved verbatim). With that gone, nothing stood against the plan's own "one order across both views" (plan.md Overview) and `sort.ts`'s claim that `orderRail` is *the* display order, of which `focusNth` was the last `sortSessions` holdout in `main.ts`.
**Dissent to honour**: Option A leaves no keyboard path to SPEC §2.1's needs-input-first rule in any configuration (in attention mode the pinned block still precedes), and in Tiles ⌘N indexes an order whose controlling `#rail-sort` is hidden with the rail.

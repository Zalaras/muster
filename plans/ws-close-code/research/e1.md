# e1 — Shutdown's `/ws` close code disagrees with the protocol

## Reproduced

Scratch daemon (scratch `-data-dir`, dedicated tmux socket `-L muster-e1-repro`, `-on-exit leave`,
updater/issue/theme/repo polls off), a Node 24 `WebSocket` client on `/ws` with the
`muster_auth` cookie, then SIGTERM to musterd:

```
cookie name: muster_auth
client: /ws open
client: msg type hello
client: msg type snapshot
client: msg type usage
sending SIGTERM to musterd
client: /ws close code=1000 reason="musterd shutting down"
daemon exit 0
error connecting to /private/tmp/tmux-501/muster-e1-repro (No such file or directory)
```

The terminal sockets (`/ws/terminal/{id}`, `/ws/shell/{id}`), the ones the protocol actually pins,
send the same code. The existing unit tests assert 1000 and pass:

```

--- PASS: TestTerminalRegistry_TakeoverAfterCloseAllClosesNewConnWithShutdownCode (0.00s)
=== RUN   TestAttachAndPump_RegistryAlreadyClosedGetsShutdownCloseFrame
--- PASS: TestAttachAndPump_RegistryAlreadyClosedGetsShutdownCloseFrame (0.03s)

$ go doc github.com/coder/websocket StatusNormalClosure

```

(Both tests assert `websocket.StatusNormalClosure`, at terminal_closeall_takeover_test.go:118 and :174.)

## Holds

**Held, but the scope is different.** The daemon sends 1000 at shutdown where the protocol says 1001.
The disagreement is on the **terminal sockets**, not on the state socket `/ws`:

- `docs/protocol.md:1656` (`kb:anchor/terminal.ws` close codes) says "Normal close (1001) on daemon shutdown".
- `docs/protocol.md:1715-1716` (`kb:anchor/terminal.shell-ws`) says "normal close (1001) on daemon shutdown".
- The state socket `/ws` also closes with 1000 (`internal/server/ws.go:99`), but `docs/protocol.md` names
  no close code for `/ws`. So that socket contradicts nothing.

The source note (`plans/maintainability-cleanup/proposed-backlog.md:58-60`) names
`wsHub.closeAll`. The review it came from (`review.work.cycle2.md:146`) names
`terminalRegistry.closeAll`, which is the correct one.

Both sides date from the first commits: the doc text came from `plans/m2-terminal/plan.md:145`
(8d488b72), and the 1000 was in the code from the same M2 commit.

## Cause

`internal/server/terminal.go:128-130`. `closeShutdown` calls
`ws.Close(websocket.StatusNormalClosure, "musterd shutting down")`, which is code 1000. It is the
only shutdown close for terminal sockets. Three callers use it: `terminalRegistry.closeAll`
(:249), takeover's second closed check (:172) and `attachAndPump`'s `errRegistryClosed` path
(:367). Its doc comment at :236 even says "normal close 1001", and the doc says 1001. RFC 6455
§7.4.1 defines 1001 "Going Away" as "an endpoint is going away, such as a server going down", and
1000 as a finished-purpose close. So 1001 is the correct code and the code is wrong. The doc's
label "Normal close" is a loose name, because 1000 is the code called "Normal Closure". The `/ws`
hub has the same literal at `internal/server/ws.go:99` (`wsHub.closeAll`). There, nothing in the
docs fixes the code either way.

No ADR covers close codes. `go tool kb for` lists none, and `docs/adr`, `docs/facts` and the
feature specs contain no 1000/1001 decision. The dashboard does not treat the two codes
differently. `web/src/terminal/overlay.ts:9-13` maps everything except 4000/4001 to
"disconnected", and its test already covers both 1000 and 1001
(`overlay.test.ts:16`). `web/src/ws.ts:104` ignores the code completely. So the change is not
visible to the user.

## Proof

- **Level**: unit (Go). The close code is a property of the daemon's close frame, and a
  `httptest` server with a coder/websocket client can observe it. The dashboard does not treat
  1000 and 1001 differently, so no render or E2E test can tell them apart.
- **File**: `internal/server/terminal_closeall_takeover_test.go`
- **Name**: `TestTerminalRegistry_TakeoverAfterCloseAllClosesNewConnWithShutdownCode` and
  `TestAttachAndPump_RegistryAlreadyClosedGetsShutdownCloseFrame`. Also, in
  `internal/server/terminal_test.go`, add a status check to
  `TestHandleTerminal_ShutdownClosesOpenTerminalSocketsNormally`. That test covers the real
  `Server.Shutdown` → `closeAll` path on a live socket, using a per-test tmux socket.
- **Failing assertion**: `assert.Equal(t, websocket.StatusGoingAway, ce.Code)` (or
  `websocket.CloseStatus(err)`). Against today's code it fails with expected 1001 / actual 1000
  (`StatusGoingAway` vs `StatusNormalClosure`).
- **Writer**: daemon-tests. These are edits to existing test assertions plus one new
  assertion. The impl agent must not touch the tests.

## Route

**fix**: change the code to match the documented protocol (`kb:anchor/terminal.ws` and
`kb:anchor/terminal.shell-ws` already say 1001). This is **not** a protocol change.
`docs/protocol.md` stays as it is in substance. The only possible doc touch is the editorial
"Normal close" → "Going away" label.

## Questions

1. **The `/ws` state socket.** Should `wsHub.closeAll` (`internal/server/ws.go:99`) also move to
   1001 for consistency? The protocol does not document a close code for `/ws`. Changing it
   without a doc line leaves the behaviour undocumented. Adding a "1001 on daemon shutdown" line
   under the `/ws` section would be new protocol text, an additive documentation of behaviour,
   not a shape change. The default if nobody decides: terminal sockets only, which is the
   minimal fix that removes the documented disagreement.
2. **The doc label.** Should "Normal close (1001)" become "Going away (1001)" in
   `docs/protocol.md` (two places)? This is editorial. The default if nobody decides: yes,
   during doc-reconcile.

Neither question blocks the core fix. If nobody answers, the safe unattended scope is the
terminal-socket code change plus the test assertions.

## Answers

Developer, verbatim: "Whatever is best practise for these types of things. If there is no clear best practise that you know or online then use the decider and continue"

Resolved by the session against RFC 6455 §7.4.1, which defines 1001 "Going Away" as the code for a server going down. That is clear best practice, so the decider was not needed:

1. **`/ws` state socket:** yes. `wsHub.closeAll` also closes with 1001 (`StatusGoingAway`). The `/ws` section of `docs/protocol.md` gains one sentence saying the daemon closes `/ws` with 1001 on shutdown. This documents behaviour and changes no message shape, so there is no protocol version bump (kb:adr/connection-protocol-bumps-only-on-shape-change). The developer authorised this documentation line here.
2. **Doc label:** yes. "Normal close (1001)" becomes "Going away (1001)" at both terminal-socket places in `docs/protocol.md`.

Proof for 1: `TestServerShutdown_ClosesOpenWSConnections` in `internal/server/ws_test.go` gains a close-status assertion of `StatusGoingAway`, which is red today.

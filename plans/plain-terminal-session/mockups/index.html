DECIDED 2026-09-05 (Damian). Focus → option B, the segmented claude | shell switch in the mainhead. Tiles → the same segmented component, in the tile footer (.tfoot .acts), not the header. The consolidated design authority both views are transcribed from is ../mockup.html; the three option pages below are kept as the record of what was compared.

Focus — the options compared

A — mainhead button

One .btn in the existing .mainhead .acts row, left of End/Resume/Remove. It names the surface it switches to ("shell", then "claude"), and goes teal with a pip while a shell is running.

+ zero new chrome; survives the session dying for free (mainhead always renders)

+ literally the spec's "one toggle control"

− sits among lifecycle actions, but it is a view switch, not an action

B — mainhead segment

A two-segment claude | shell switch in the mainhead, reusing the Settings dialog's own .seg-track idiom. Both surfaces are named at all times; the pip sits on the shell segment.

+ reads unmistakably as "two surfaces of one session", not as an action

+ current surface is always legible without inferring it from the label

− wider than A; a second control group in an already-busy header

− two controls, where the spec asked for one

C — pane tab strip

A tab band between the mainhead and the terminal — the most literal reading of the spec's "in the pane area". Room for the cwd on the right.

+ the only option that grows into the deferred follow-up (several shells, a real tab strip)

− a whole new horizontal band; costs ~30px of terminal height in Focus

− no Tiles twin: a tile cannot afford a third band, so Tiles would diverge

Tiles — measured, and it changes the spec

tiles.html renders the 3×2 grid with the control in the tile header or the tile footer (demo bar switches). Spec §Scope says the tile control goes in .thead "without displacing any of them … only the title's existing ellipsis may absorb the width". Measured against the shipped header, that is not true at 3×2 on a smaller window:

1152px viewport · 383px tilestitles truncatedrepo/branch truncated
no control at all (today)1 / 61 / 6
control in .thead (as specced)6 / 66 / 6
control in .tfoot .acts1 / 61 / 6

The single truncation in the good rows is worktree-conflicts-spike, a title long enough to truncate today with no control present. At a 1512px viewport (503px tiles) every arrangement fits, which is why this only shows up if you measure at a realistic smaller window.

What the measurement says. .thead's .nm and .wh share the same flex shrink, so anything added to that row is paid for by both the title and the repo/branch — the spec's "only the title absorbs it" isn't a rule the header's layout can honour. Shrinking the control to an icon (>_, 27px instead of 45–61px) only gets it from 6/6 back to 4/6; it does not fix it. The footer is the fix: .tfoot is geo · marker · acts, carries no shrinking text, already holds the End button, and puts the header back to exactly its no-control baseline.

What was picked, and why

  • Focus → A, unless you want the follow-up shape now. B costs header width for a legibility gain that the pip already mostly delivers; C is the nicest read but breaks Focus/Tiles symmetry and spends terminal height on a control you'll press rarely.
  • Tiles → the footer, on the measurement above. It also lands the tile control next to End, which pairs with A putting the Focus control next to End/Resume/Remove — the two views stay symmetric, which is the thing C would have cost us.
  • Dead sessions need no rework. In all three options the control sits above/outside the pane area, so it survives alive:false untouched: the claude surface becomes the existing ended-snapshot + cap, the shell surface stays a live shell. Flip session → ended on any page to see it. The only real change is that #dead-surface stops being "what the Focus pane shows when dead" and becomes "what the claude surface shows when dead" — a condition change in renderFocusView, not a redesign.

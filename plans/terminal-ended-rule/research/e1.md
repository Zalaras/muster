## Holds

Yes, both cases.

## Cause

Web: `web/src/features/surfaces.ts:179-185` `observeSpawnReply` tests `rev <= seenRev(revState, id)`,
and `seenRev` (`web/src/terminal/terminalsrev.ts:8`) is one number per session raised by lists **and**
by every reply (`observeReply`, surfaces.ts:187-191, and observeSpawnReply itself, :183). A rename/close
reply therefore lifts the "ended" threshold above a spawn reply's rev before the list carrying the new
terminal is applied, and `getTerminals` still lacks n → ended. The state has no "rev of the last list
applied" separate from the stale-list floor.
Daemon: `internal/server/shellactivity.go:130-138` `tick` (via `sync`, :126, wired as `changed` in
`server.go:225`) returns silently when the lister fails, so `revs[id]` is unchanged and the routes
(`internal/server/shells.go:144,155,168` and rename :209-210, delete :239-240) answer the session's old
rev — at or below what the window already applied — and nothing marks the session for a forced
re-broadcast, since `reconcile` (:179) only broadcasts lists that differ.

## Questions

1. The fresh rev raises the daemon-wide counter, which is what `snapshot.terminalsRev` reports
   (protocol ws.shell-activity: "its value when the snapshot was built"). A window that reconnects and
   applies a snapshot built after the failed listing but before its spawn reply lands will see
   rev ≤ applied and a list lacking n → ended. Narrow (reconnect mid-request plus a failed listing);
   suggested default: accept as written by the contract — no change. Otherwise the snapshot would
   have to report the last *broadcast* rev, which the protocol does not say.
2. Seam shape for the per-session fresh rev (pass session id into `changed`, or have sync report
   failure and the route call a `freshRev(id)`) — impl's choice, no contract impact. Not a blocker.

## Decisions

- REQ-1 through REQ-5, REQ-11, REQ-12 (cache/atomic-write mechanics): daemon-impl's side — nothing web-side to do beyond consuming `GET /api/models`'s contract, which `checkModels`/`parseModelVerdicts` do.
- REQ-6: both halves implemented — `openModal()` requests the four presets unconditionally; `applyModelRestore()` (called from both `applyInitialRestore` and `selectRecent`) requests the restored model's own verdict whenever it isn't a preset.
- REQ-7/REQ-8: `deriveModelRowState` excludes the currently-selected preset from `disabledPresets` by construction (`isCurrentSelection` in its loop), so REQ-7's disable and REQ-8's mark are mutually exclusive on one radio without a separate composition step.
- REQ-9: implemented by folding the launch-time refusal into the same `VerdictStore` (`applyVerdicts(modelVerdicts, modelVerdicts.generation, [{model, verdict:"unrecognized", message}])`) rather than a bespoke "mark this one field" path — it reuses REQ-8's exact mechanism for whichever control (preset or custom) currently holds the refused model. Verified against the E2E spec: the pre-existing (E6) test still expects `#launch-error` to show the same message on this refusal, so `showError(...)` is kept unconditionally; the new REQ-9 test additionally asserts `#model-error` fires too — both fire together, matching the authored test file exactly (`web/e2e/launch-model-check.spec.ts:254,263-264`).
- REQ-10: a failed `checkModels` (network/daemon-down) never calls `applyVerdicts`, so `modelVerdicts` is untouched and derives exactly the "no data yet" state — no separate branch needed.
- REQ-13 (staleness): design: the plan's two edge cases (dialog closed; custom text edited) need different mechanisms, and only one needed new code. "Custom text edited" needs nothing extra — `deriveModelRowState` always looks up `verdicts.get(selection.selected)` against the *current* text, so a verdict landing under the old text is simply never read. "Dialog closed and reopened" is the real hazard (an out-of-order stale response could overwrite a newer generation's correct verdict), so `VerdictStore` carries a generation bumped once per open (`resetVerdictStore`, called from `resetForm()` only — never per-request), and `applyVerdicts(store, generation, models)` drops the whole batch when `generation !== store.generation`. This is deliberately *not* per-request (unlike `navigate()`'s `browseRequestId`): the four-presets request and a later restored-custom-model request within the same open must both merge regardless of arrival order, so the counter is scoped to the dialog session, not the individual fetch.
- design: reused the existing "capture a counter, compare on arrival" idiom already in this file — `rg -n "requestId !== browseRequestId" web/src/features/launch.ts` → one hit (`navigate()`) — cited in `launchmodels.ts`'s doc comment on `applyVerdicts`, applied at dialog-open granularity instead of per-navigation (see REQ-13 above for why the granularity differs).
- design: `launchmodels.ts` placement follows the plan's Affected Files instruction and matches `features/CLAUDE.md`'s own list of "a DOM-free decision with exactly one controller caller" modules (`launchcrumbs.ts`, `launchrestore.ts` are the existing siblings in this same shape) — `launch.ts` is its one caller, so it belongs beside it, not in `sessions/` or `render/`.
- design: `render/launch.ts`'s new `renderModelRowState` imports `ModelRowState`/`ModelSelection` as `import type` from `features/launchmodels.ts` — a type-only, zero-runtime-effect import for the parameter shape, rather than duplicating the same two interfaces locally. Checked for precedent first: `rg -n '"\.\./features' web/src/render/*.ts` finds two hits, but both are in `.test.ts` files only (`masthead.test.ts`, `update.test.ts`) — no shipped `render/*.ts` source file imports from `features/` today. I judged the type-only import to be within the existing "a builder takes the computed value" rule (it takes the value; the type import only names that value's shape) rather than a new precedent to avoid, since the alternative (two structurally-identical interfaces, one per file) is pure duplication with no behavioural difference. Flagging this as a judgment call for review rather than asserting it as settled precedent.
- `web/src/features/launch.ts` size-warning (`make size-warn`: `file is 580 lines (threshold 500)`) kept on purpose: the file was already over threshold before this plan (504 lines at `HEAD`, confirmed via `git show HEAD:web/src/features/launch.ts | wc -l`). The added ~75 lines are DOM-wiring glue (event listeners, the verdict-store field, five small controller functions) that `docs/conventions.md` § Composition roots keeps in the controller — the pure derivation is already extracted to `launchmodels.ts`, so splitting further would fragment one controller's cohesive open/restore/submit flow rather than remove real duplication.
- Every REQ-1 through REQ-13 the plan lists for the web side appears above in Changes/Decisions; REQ-1 through REQ-5/11/12 are explicitly noted as daemon-only with no web action.

**How the two paths are told apart** (per the scope note): there is exactly one call site that passes `true` — `submit()`'s refusal branch, which only runs in response to the developer's own launch attempt (Enter anywhere in the form, or a click/Tab+Enter on Launch). The two paths are structurally distinguishable by call site, not by inspecting any runtime flag, so there is no way for a dialog-open verdict to accidentally take the new branch.

**Precedent / blast radius**: `rg -n "renderModelRowState" web/src web/e2e` → two hits, both in `features/launch.ts` and `render/launch.ts` (the declaration and its one call site); no test file calls `renderModelRowState` or `updateModelRowState` directly (`web/src/render/launch.test.ts` only tests `renderLaunchFooter`; there is no `features/launch.test.ts`), so widening the signature with a defaulted parameter is the only consumer touched and needed no test-file changes.

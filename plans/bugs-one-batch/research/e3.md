## Holds

The bug held as written. It is wider than the report says:
- The seven-day bucket has the same flaw.
- So does the per-model window, because it uses the same view model.

The report's context ("session failed") fits `kb:fact/status-line-around-failed-turns`. A 429 at 100% carries the rate-limit headers, so that session's last post recorded 100%. After that, nothing posts again: the session is failed or idle, and there is no `refreshInterval`.

## Cause

The 5h and 7d buckets have only one source: a routed status post. The path is `internal/server/ingest.go:194-210` into `Aggregator.Record`. `Aggregator.Current` (`internal/usage/aggregator.go:100-118`) returns the last sample for as long as the daemon runs, whatever its `ResetsAt`. Nothing anywhere compares `resetsAt` to the clock:
- The daemon serves the stale bucket on every snapshot (`internal/server/usage.go:102-104`), so a page reload changes nothing.
- The web derivation `buildUsageBucketViewModel` (`web/src/sessions/usage.ts:40-47`) renders `usedPct` and the past reset time as they are, even though the render loop passes it `frame.now` every second.

The refresh button (`web/src/features/usage.ts:75-87` → `POST /api/usage/refresh`, `internal/server/usage.go:110-117`) only wakes the per-model poller. `InterpretUsageReport` (`internal/claudecode/usageapi.go:110-136`) reads only `limits[]` rows of kind `weekly_scoped`. It ignores the response's `five_hour`/`seven_day`, although `kb:fact/usage-api-oauth-shape` records that they are there. So the refresh cannot touch the 5h gauge by design (`kb:adr/usage-model-window-polled-from-oauth-api` scoped the poll to the per-model window).

## Proof

- **Level:** unit. This is pure derivation logic (kb:adr/process-test-levels-journey-property-logic). No daemon or DOM is needed to falsify it.
- **File:** `web/src/sessions/usage.test.ts`, written by **web-tests**.
- **Test name:** `buildUsageBucketViewModel — a bucket whose resetsAt has passed does not show the pre-reset percentage`.
- **Input:** `buildUsageBucketViewModel({ usedPct: 100, resetsAt: <NOW − 1h> }, NOW)`.
- **Assertions:** `vm.percentText` is not `"100%"` but the decided post-reset value, and `vm.warn` is `false`.
  - Today it returns `percentText: '100%'`, `warn: true`, `fillPercent: 100` (measured above).
  - A second case pins the boundary: `resetsAt` 1 minute in the future still shows `"100%"`.

**Render-test hazard.** The render fixture normaliser moves timestamps to the fixture epoch plus whole minutes, and the page clock starts at that epoch. The first walked timestamp therefore equals "now" at load. Make the comparison strict (`resetsAt < now`, not `<=`) and run `make render-test`. That keeps an existing usage render fixture from flipping its 5h bucket to the post-reset readout. No new render test is needed, because the view model is the whole behaviour.

`fix` for A (web derivation only, no wire change).

## Questions

1. **What does a bucket past its `resetsAt` show, when no fresh sample has arrived?** The options are:
   - **(a) `0%`** with no reset time. The window really has reset, but any use since then (for example Claude Code run outside Muster) would read as 0.
   - **(b) the word `unknown`** with no track (`kb:adr/usage-unknown-renders-word-not-track`). The code comment in `usage.ts:13-14` already says "never a percentage guessed from a stale or absent sample".
   - **(c) a "reset" word**, which is a new readout.

   Recommendation: (b) or (a). (b) needs no new copy and matches the honesty rule.
2. **Should the refresh button also refresh the 5h/7d bars** (fix B: read `five_hour`/`seven_day` from `/api/oauth/usage` into the aggregator)? The issue's expected behaviour names the refresh button explicitly. B is a protocol-prose change and widens an accepted ADR's scope, so it is not small-track. If wanted, it should go to `/spec` + `/orchestrate` as a separate item. Fix A alone resolves the visible symptom without a refresh, because the readout flips at the reset instant on the next render tick.

# e9 — The pop-out reader keeps the old dashboard after Update and restart

## Reproduced

Scratch Playwright spec outside the repo (`<scratchpad>/e9/popout-reload.spec.ts`, own config, importing `web/e2e/helpers/fixtures` by absolute path, `bin/musterd` built 2026-10-21, no relevant web change since). It uses the same routed-`/ws` technique as `update.spec.ts` › "a window holding a restart record reloads on a mismatched-protocol reconnect…". The steps: launch a session, open `/doc.html?session=…&path=<abs>`, set a `window.__e2eMarker`, push a synthetic `update` broadcast with `apply.phase: "restarting"` down the pop-out's socket, close the server side so the pop-out reconnects, then check the marker.

```
$ cd web && nvm use && npx playwright test --config <scratchpad>/e9/pw.config.ts

status before: file no longer exists — /var/folders/.../muster-e2e-repo-2c6a18c1-rxStc6/README.md
ws connections: 2
load events after restart record + reconnect: 0 marker: before-restart
  ✘  1 [chromium] › …/e9/popout-reload.spec.ts:5:1 › e9 repro: a pop-out holding a restart record reloads on the next hello (3.9s)

    Error: pop-out should have reloaded (marker gone)

    expect(received).toBeUndefined()

    Received: "before-restart"
```

The pop-out reconnected (2 sockets) and got its new hello, but it never reloaded: there were 0 load events and the pre-restart marker survived. The same steps on the dashboard page reload it (the existing E2E proves this).

## Holds

It holds as written. The daemon already sends the `update` broadcast to every `/ws` client: `internal/server/update.go:82` calls `hub.broadcast(updateMessage{…})`, and the pop-out opens its own socket (kb:adr/reader-popout-is-a-second-page). The pop-out never hears it because its page does not wire the handlers. This also contradicts `docs/features/update/spec.md:52-55`: "Every window that saw the restart … reloads on its first reconnect".

## Cause

`web/src/doc.ts:31` builds the pop-out's `WsClient` with `coreWsHandlers(app, connection)` only, and never calls `initUpdateRestart`. `coreWsHandlers` (`web/src/wsapp.ts:31-62`) has no `onUpdate` and no `onHelloArrived`. Only `dashboardWsHandlers` (`web/src/wsapp.ts:93-104`) relays those two signals onto the app bus as `"update"` and `"helloArrived"`. `features/updaterestart.ts:115-152` listens for those two events to hold a restart record and then `location.reload()` on the next hello. As a result the pop-out's `ws.ts` dispatch (`web/src/ws.ts:132`, `:166`) calls `onHelloArrived?.()` and `onUpdate?.()` on undefined handlers, so no record is ever held and nothing reloads. The header comments in `doc.ts:9-10` and `wsapp.ts:3-5` say this was deliberate ("no feature on this page reads any of them"). That was true before settings-update-failures added the reload, and the pop-out was left out on purpose (`plans/settings-update-failures/proposed-backlog.md`, "Pre-existing: no").

## Files

The fix is web-only. In `doc.ts`, call `initUpdateRestart(app)` before the socket starts. Then make the pop-out's handlers relay `onUpdate` to `app.emit("update")` and `onHelloArrived` to `app.emit("helloArrived")`. There are two ways to do that. One is a small `popoutWsHandlers` in `wsapp.ts` that spreads `coreWsHandlers` and reuses the dashboard's two relays (factor them so neither copy diverges). The other is to move those two relays into `coreWsHandlers`. Either way, no protocol change: `update` and `hello` are already on the wire to every client. The pop-out has no banner, so the handle's `bannerOverride` and the "Updated to" confirmation simply go unread there. `reloading()` is not needed either, because the pop-out wires no `onProtocolMismatch`.

- `web/src/doc.ts`: wire `initUpdateRestart` and the new handlers, and update the header comment. kb: feature **reader**; diagram `kb:diagram/web-components`.
- `web/src/wsapp.ts`: add the pop-out handler set (or move the two relays into core), and update the header and doc comments that say the pop-out has no feature for update or hello-arrived. kb: feature **connection**; diagram `kb:diagram/web-components`.
- `web/src/features/updaterestart.ts`: no logic change expected. Its header comment says hello arrival is "wired in wsapp.ts" and it can stay, but check its "this window" wording. kb: feature **update**; `kb:adr/update-restart-reloads-dashboard`, `kb:adr/process-one-name-per-feature`; diagram `kb:diagram/web-components`.
- `web/e2e/update.spec.ts`: the new E2E (below). kb: feature **update**; `kb:adr/process-test-levels-journey-property-logic`.
- `web/src/wsapp.test.ts` (optional unit coverage of the new handler set). kb: feature **connection**; diagram `kb:diagram/web-components`.
- Docs for doc-reconcile and the diagram:
  - `docs/diagrams/web-components.md:79`: `Rel(doc, features, "reader, connection, theme")` gains `update`. The diagram names `doc.ts`, so it must change in the same commit.
  - `docs/features/update/spec.md:52-55`: keep "every window … reloads" and say that only the dashboard shows the banner and confirmation.
  - `docs/features/reader/spec.md:69-73`: the pop-out paragraph can add that it reloads after an update restart.

  No new ADR is needed. `kb:adr/update-restart-reloads-dashboard` already says "a window that saw an update restart … reloads on reconnect", and the fix brings the pop-out into line with it.

## Proof

- **Level:** E2E. The claim is a journey across a socket drop and reconnect to a live daemon, ending in a real navigation of the second page. The wiring lives in `doc.ts`'s side-effecting composition root, which no unit or render test runs. A `wsapp.test.ts` unit test of the handler set would only prove the relay, not that the pop-out reloads.
- **File:** `web/e2e/update.spec.ts`, beside "a window holding a restart record reloads on a mismatched-protocol reconnect…". It uses the plain `daemon` fixture and the same routed-`/ws` technique: push a synthetic `update` broadcast with `apply.phase: "restarting"`, then `server.close()`. No real download or restart.
- **Test name:** `"an open pop-out reader holding a restart record reloads on its first reconnect (REQ-16)"`.
- **Failing assertion today:**
  - `await page.waitForEvent("load", { timeout: 10_000 })` times out, or equivalently `expect(await page.evaluate(() => window.__e2eMarker)).toBeUndefined()` receives `"before-restart"`.
  - After the reload, `readerStatusLine(page.locator("#reader-host"))` is connected again, and the URL still carries `session=` and `path=`, so the same document reopens.
- **Writer:** e2e-specs.

`fix`. Web-only, no protocol change, no new spec and no new UI surface. It brings the pop-out into line with the existing update spec's "every window" sentence and the accepted ADR.

The reader keeps the open file: the same doc came back each time and `openPath` is in memory. The scroll position is not kept: 600 became 0 on all three paths (docs→shell→docs, docs→claude→docs, and session A→B→A). The `article.md` node is a new element after every switch.

## Holds

Held as written, for both tab switches (shell and claude) and for session switches in Focus. The same cause also covers:

- Tiles: a tile's reader is disposed when that tile leaves `docs` or stops being visible.
- A full page reload: the instance is rebuilt and nothing stores the scroll position.

The pop-out (`doc.ts`) has no surface segment, and its single instance is only disposed on `sessionRemoved`, so it does not lose its place on a switch. It does lose it on a reload of the pop-out.

## Cause

`web/src/features/reader.ts:589-598`: `reconcileInstances` keeps a `ReaderInstance` only while its session is visible *and* has `docs` selected. Otherwise it calls `instance.dispose()`, which removes the whole reader root at `:212`.

Coming back builds a fresh instance. It re-reads `ReaderMemory`, re-fetches, re-opens `memory.openPath` (`:266`), and puts a new fragment into a new body (`:318`), so `scrollTop` is 0.

`ReaderMemory` (`web/src/reader/memory.ts:4`, key `muster.reader.<sessionId>`) holds `openPath`, `clearedAt`, `expanded` and the two folds, but no scroll position. Nothing restores the position after the body renders.

The fix for the expanded-folders version of this bug (#82, plan `reader-expanded-persists`, done 2026-10-12 via `/fix`) added `expanded` and the folds to this same memory. It did not add scroll.

## Questions

1. **Per document or per session?** Option (a): one position per session+document, so A→B→A inside one session restores each. Option (b): only the open document's position, dropped when another file opens.
   - Recommendation: (a), since the issue says "the scroll position in a document".
   - Cost of (a): the map grows per opened file, so it needs a cap or pruning (e.g. drop entries for paths no longer in the listing). Cost of (b): a single field.
2. **Survive a page reload?** Option (a): store the position in the existing localStorage `ReaderMemory`, matching `openPath`/`expanded`, which already survive reload. Option (b): keep it only in an in-memory map in `initReader`, which survives a switch but not a reload.
   - Recommendation: (a), which follows the #82 precedent and `kb:adr/reader-memory-split-browser-and-daemon`.
   - Consequence: the memory is shared live with the pop-out through the `storage` event. The fix should **not** scroll a reader that is already showing in the other window when that event arrives; the stored position should only apply when a reader is built.
3. **If the document changed on disk meanwhile:**
   - Recommendation: restore the same pixel offset, clamped to the new `scrollHeight - clientHeight`. This is simplest and matches how a live `docChanged` re-render behaves today (the offset stays as is).
   - Alternative: anchor to the heading at the top (scroll-spy's `currentHeadingId`) and scroll that heading into view. This is more robust to edits above the reading point but loses the offset within a section, and becomes ambiguous if the heading was removed.


## Answers

Developer, verbatim (2026-10-22): "2 confirmed." / "Ok drop 3 from this batch" / "The other’s I didn’t mention we’re going with your suggested default"

Go, defaults:
- 5a: one scroll position per session + document, so switching between documents inside a session restores each. The map is capped or pruned (e.g. drop paths no longer in the listing).
- 5b: it survives a page reload: stored in the existing localStorage ReaderMemory. A stored position applies only when a reader instance is built; it never scrolls a reader already showing in the other window.
- 5c: if the document changed on disk, restore the same pixel offset, clamped to the new scrollHeight − clientHeight.

It imports the real `web/e2e/helpers/{fixtures,effort}.ts`, takes the per-test `daemon` fixture, and runs on the existing `bin/musterd` (built 2026-10-21; `web/src` has not changed since 5fbd016e, so the served bundle is current). ## Holds

The claim holds as written. After the daemon comes back, the masthead reads `connected` and the banner is hidden, but `#action-error` still shows `Could not reach musterd.` 3 s later.

Scope:
- **Where the message shows.** It appears in one place, the global `#action-error` line (`web/index.html:57`). Its only writer is `actions.showError` / `showActionError`. That line is fed by:
  - Stop, Resume and Remove from the mainhead, rail card or tile footer;
  - batch Stop and Remove;
  - group moves (`features/groups.ts:164`, `groupsdialogs.ts`);
  - rename;
  - effort Dismiss (`features/effort.ts:15`).
- **How a down daemon gets there.** While the connection is down, most of those controls are disabled, so in practice the message comes from Dismiss. It can also come from a click in the short gap before the WebSocket notices the drop.
- **Dialog error lines are a separate case.** The launch dialog's own `#launch-error` and the issue dialog's error regions can also show `Could not reach musterd.`. They are separate regions and are outside this entry. The issue dialog closes on a disconnect (`app.on("status")`). The launch dialog does not subscribe to `status`.

## Cause

`web/src/features/actions.ts:97` (`showActionError`) is the only writer of `#action-error`, and it clears the line only when a later action succeeds (lines 172/184/195, `groups.ts:164`, `effort.ts:15`).

Nothing subscribes to the connection coming back:
- `features/connection.ts:109` emits the `status` event only for statuses other than `connected`. `actions.ts:277` uses it only to close the confirm dialogs.
- The `helloArrived` event that fires on every hello (`wsapp.ts:95`, emitted on the bus per `app.ts:72`) has only one listener, `updaterestart.ts:147`.

So a `network_error` body (`web/src/api/http.ts:43-46`) written while the daemon was down stays until the next action overwrites it.

## Files

- `web/src/features/actions.ts` — the fix. Subscribe to the reconnect (`app.on("helloArrived", …)`, or a `status`/connected transition) and clear `#action-error`. To clear only the unreachable message, `actions.ts` must know the shown message's origin. Two ways: compare against the `network_error` body, or have `showError` take the `ApiErrorBody`/code.
  - kb: feature **actions**; `kb:diagram/web-components`; `kb:adr/actions-bulk-stop-remove-are-daemon-batches`; `kb:adr/process-one-name-per-feature`.
- `web/src/api/http.ts` — only if the fix compares against the shared message or code. It would export `networkError` or its code constant; today the code is a module-private literal.
  - kb: feature **connection**; `kb:diagram/web-components`; `kb:adr/connection-commands-http-ws-push-only`.
- Possibly `web/src/features/groups.ts`, `groupsdialogs.ts` and `effort.ts`, if `showError`'s signature changes to carry the code.
  - kb: features **groups** and **focus** respectively, same `web-components` diagram.
- Test: `web/e2e/effort-header.spec.ts`.
  - kb: feature **focus**; `kb:adr/process-test-levels-journey-property-logic`.

## Route

`fix`. There is no protocol change: `helloArrived` and `status` are existing client-side bus events. There is no new spec and no new UI surface.

## Questions

1. **Which messages clear on reconnect: only the unreachable one, or any action error?**
   - **Only the unreachable message.** Recommended default, and it matches the entry. A real daemon refusal is still true after a reconnect, so it would stay, for example "group deleted" or a partial batch report from before the drop. This needs `actions.ts` to know the shown message's code.
   - **Any action error.** This is the simpler one-line fix, but a reconnect would wipe a refusal the user may not have read yet.
2. **Should the launch dialog's own error line also drop a stale `Could not reach musterd.` on reconnect?** It is a separate region and not named in the entry. The suggested default is no; leave it out of scope.

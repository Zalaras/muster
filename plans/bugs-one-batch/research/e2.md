# e2 — Right click menu with multiple select only applies action to one (#97)

## Reproduced

The behaviour is reproduced by the existing E2E test that asserts it as intended behaviour. That test
selects A and B, right-clicks selected card A, chooses `No group`, and asserts that only A moved
while "2 selected" is kept:

```
$ make e2e SPECS='e2e/rail-menu.spec.ts -g "Select mode opens the same single-session menu"'
...
cd web && npm run e2e -- e2e/rail-menu.spec.ts -g "Select mode opens the same single-session menu"
e2e-lint: clean
Running 1 test using 1 worker
  ✓  1 [chromium] › e2e/rail-menu.spec.ts:424:1 › right-clicking a card in Select mode opens the same single-session menu and the selection stays as it was (REQ-7) (3.0s)
  1 passed (9.1s)
```

The test body (web/e2e/rail-menu.spec.ts:451-458) shows what the issue reports: `No group` on A leaves
A's group null and B still grouped (`expect((await stateSession(page, daemon, b.id)).groupId).not.toBeNull()`).

## Holds

The symptom holds as written. The menu acts on one card only. But this is **designed, specified
and tested behaviour, not a defect**:
- kb:adr/rail-card-right-click-menu-holds-session-actions (accepted 2026-10-14): "In Select mode the
  menu is for the one card and leaves the selection alone."
- plans/rail-card-organise/spec.md item 5 and plan.md REQ-7: "Right-clicking a card in Select mode
  opens the same single-session menu; the selection is unchanged."
- web/e2e/rail-menu.spec.ts:424 (REQ-7) guards it.

So fixing #97 reverses an accepted ADR and an E2E-guarded requirement. That makes it a behaviour
change the developer must decide, not a bug fix.

## Cause

`web/src/features/railmenu.ts:56-67`: `open({ id, card, at })` looks up the one session by `id`,
builds `cardMenuItems(session, …)` (`web/src/features/railmenuitems.ts:48`) and `entriesFor(session, items)`,
whose `act` closes over `session.id` (`railmenu.ts:27`). `deps.groups.moveToEntries(session, …)`
wraps it as `[session]` (`groups.ts:482`). `RailMenuDeps` has no access to the selection
(`groups.selecting()` / `selectedIds()`), so the menu cannot act on many. The card's `contextmenu`
listener (`web/src/render/sessions.ts:300`) passes only the card's own id. All of this is as the
ADR decided.

- `web/src/features/groups.ts`: expose `moveToEntries(sessions[], …)` for many (today it is
  wrapped as `[session]` at :482). kb: feature groups; kb:diagram/web-components;
  kb:adr/process-one-name-per-feature, kb:adr/rail-group-name-click-does-not-fold,
  kb:adr/rail-select-mode-persists-across-bar-actions.

  passes both handles; only the structural `RailMenuDeps` type widens. kb: feature connection; composition-root ADR
  kb:adr/process-composition-roots-registration-only plus the others listed for main.ts.
- `web/e2e/rail-menu.spec.ts`: the REQ-7 test (line 424) must be rewritten. kb: feature rail;
  kb:adr/process-test-levels-journey-property-logic.
- Docs: a new ADR superseding kb:adr/rail-card-right-click-menu-holds-session-actions (an accepted
  decision cannot be edited). Also `docs/features/rail/spec.md` (lines 36-38), `docs/features/groups/spec.md`

No protocol change is needed for Stop, Remove and Move to. `sessions.end-many`, `sessions.remove-many`
and `sessions.group` (ids list) already exist and are used by the selection bar. Resume and Pin have
no batch endpoint, so offering them for many would mean a dashboard loop. That breaks
kb:adr/actions-bulk-stop-remove-are-daemon-batches in spirit, or needs a protocol change.

## Proof

- Level: E2E. It is a journey: the menu's choice reaches the daemon for several sessions and the
  state comes back. That matches the existing REQ-7 test's level. The pure item list could add a
  unit test.
- File: `web/e2e/rail-menu.spec.ts`. Rewrite the test at :424, e.g. "right-clicking a selected card
  in Select mode applies the menu's action to the whole selection".
- Failing assertion today: after selecting A and B and choosing `No group` from A's menu,
  `expect.poll(() => stateSession(page, daemon, b.id).groupId).toBeNull()` fails, because B stays
  grouped. Likewise, `Stop…` from A's menu should open the count confirm ("Stop 2") and end both.
- Agent: e2e-specs (with web-tests for any `railmenuitems.ts` unit cases).

## Route

`fix` only if the developer decides to reverse the ADR and keeps it to Stop/Remove/Move to (no
protocol, no new surface; the menu already exists). The fix must ship a superseding ADR. If Resume
or Pin for many is wanted, it is `not-small-track: protocol` (no batch endpoint exists).

## Questions

1. **Reverse kb:adr/rail-card-right-click-menu-holds-session-actions?** It deliberately says the menu
   is for the one card in Select mode (REQ-7 of rail-card-organise, E2E-guarded). Applying to the
   selection supersedes it. Yes, or close #97 as working as designed?
2. **Which items apply to many?** The proposal: Stop…, Remove… and Move to act on the selection
   (daemon batches exist, confirm with the count as the bar does). For Resume and Pin/Unpin, either
   drop them from the multi menu, or make them protocol work (out of small track).
3. **Right-clicking an unselected card while others are selected:** the proposal is a single-card
   menu as today, which matches how an unselected card does not drag the selection
   (kb:adr/rail-cards-drag-in-both-sort-modes-selection-together). The alternatives are to replace the
   selection with that card, or to add it.
4. **Should the menu label say so** (e.g. `Actions for 3 sessions`), and do mixed live/ended
   selections show Stop and Remove together? The bar enables Stop when any is alive.
5. Interaction with #98 (should select mode end after an action): kb:adr/rail-select-mode-persists-across-bar-actions
   keeps the mode after bar actions. Presumably a menu action on the selection keeps it too.


## Answers

Developer, verbatim (2026-10-22): "2 confirmed." / "Ok drop 3 from this batch" / "The other’s I didn’t mention we’re going with your suggested default"

Go, with every default confirmed after the developer asked what general practice is (Finder, Explorer, Gmail and VS Code: a right-click on a selected item acts on the whole selection, the menu names the count, and items that cannot apply to many are hidden or greyed):
- 2a: reverse kb:adr/rail-card-right-click-menu-holds-session-actions with a superseding ADR. In Select mode, right-clicking a card that is in the selection opens a menu acting on the whole selection.
- 2b: Stop…, Remove… and Move to apply to the selection, each confirming with the count as the selection bar does. Resume and Pin/Unpin are hidden in the multi-session menu.
- 2c: right-clicking a card outside the selection opens today's single-card menu for that card and leaves the selection as it was (VS Code's behaviour, and how dragging an unselected card already works).
- 2d: the menu shows the count (e.g. a heading or labels naming "3 sessions").
- 2e: with live and ended sessions mixed, Stop and Remove both show and each applies to the sessions it fits, matching the selection bar.
- 2f: Select mode stays on after a menu action (kb:adr/rail-select-mode-persists-across-bar-actions).
The REQ-7 E2E test at web/e2e/rail-menu.spec.ts:424 is rewritten to the new behaviour.

# e7 — A hard wheel flick swallows the next wheel the other way

## Reproduced

The real `accumulateWheelDelta` (bundled from `web/src/terminal/shellkeys.ts` with esbuild into the scratchpad, not the repo) fed exactly what `pane.ts` `flushWheelScroll` feeds it: one hard downward flick frame, then wheel-up frames.

```
$ npx esbuild src/terminal/shellkeys.ts --format=esm --outfile=$S/shellkeys.mjs && node $S/repro.mjs
flick down deltaY=+10000 -> lines=-200 carry=6000
wheel-up #1 deltaY=-100 -> lines=-200 carry=1900
wheel-up #2 deltaY=-100 -> lines=-90 carry=0
wheel-up #3 deltaY=-100 -> lines=5 carry=0
wheel-up #4 deltaY=-100 -> lines=5 carry=0
...
```

(`lines` > 0 scrolls back into history, < 0 scrolls toward the bottom.) The first two wheel-ups after the flick send `scroll` frames going **down** (`-200`, `-90`); the pane only starts scrolling up on the third. The carry stays put between gestures, so the swallow happens however long after the flick the next wheel-up comes.

## Holds

Held as written. The cause is on the web side only. The daemon (`internal/server/shells.go:395` → `tmux.ScrollCopyMode`) has no queue: it handles each frame once, synchronously. The swallowed wheel-ups are real scroll-down frames that do nothing, because the pane is already at the bottom. A hard flick *up* past the clamp has the same problem in the other direction (`-5000` leaves `-1000px` carried, so it eats the first wheel-downs).

## Cause

`web/src/terminal/shellkeys.ts:83-87` (`accumulateWheelDelta`). When the summed `deltaY` gives more than `MAX_SCROLL_MAGNITUDE` (200) lines, `wheelDeltaToScrollLines` (`shellkeys.ts:68-76`) clamps the frame to 200. But `accumulateWheelDelta` subtracts only the consumed `lines * PIXELS_PER_LINE` and carries the rest (`sum + lines*20`). The carry is unbounded: +10000px leaves 6000px. `pane.ts:188-190` stores that carry in `wheelAccumDeltaY`, and the next wheel event of the opposite sign is added to it. That event's small negative `deltaY` cannot outweigh the large positive carry, so the result keeps the old sign until the carry is paid down. Nothing in the accumulator resets the carry when the direction reverses.

## Files

- `web/src/terminal/shellkeys.ts`: the fix. When `eventDeltaY` is non-zero and its sign is the opposite of `accumDeltaY`, drop the carry (start from `eventDeltaY` alone). Same-direction carry, including past the clamp, stays as it is, so the pinned test `a sum past the 200-line clamp carries the unconsumed pixels to the next frame` stays green.
  `kb for`: feature **surfaces**; diagram `kb:diagram/web-components`. No ADR or fact governs the carry.
- `web/src/terminal/shellkeys.test.ts`: the new red test.
  `kb for`: feature **surfaces**; diagram `kb:diagram/web-components`.
- `web/src/terminal/pane.ts`: **not touched** (it already passes the frame's whole pending delta to the accumulator).

## Decisions

- design: `writeChain map[int64]chan struct{}` + `nextWriteTurnLocked`/`finishWrite` is a per-session ticket/turnstile: a ticket is drawn (the map entry swapped for a fresh channel) while the caller still holds `m.mu`, so tickets are handed out in exactly mutation order; `finishWrite` waits on the previous ticket's channel before persisting, and always closes its own before returning (success or failure) so persist *and* broadcast order both follow mutation order deterministically — not dependent on Go's mutex fairness. `rg -n 'rollbackOnPersistFailure|persistAndBroadcastRail' internal/session` before starting showed the existing shared tail (`rollbackOnPersistFailure`) already generalised restore-on-failure for 3 of 14 sites; I extended that seam rather than inventing a second one. Writers: every `Manager` method that persists a `Session` row or snapshot (14 existing + `MarkPlanWritten`). Guard: `m.mu` itself, map access only, same discipline as the adjacent `idLocks` field.
- design: `cloneRestore(prev *Session) func(*Session)` replaces every method's bespoke "capture these N fields, write them back" closure (RecordLaunch had 2 fields, RecordResume had 5, markEnded had 2) with one clone-and-reassign line, since `Session.Clone()` is already a full value copy and Critical 1's fix means every pointer field (Model/Context/Attention/Failure) is safe to restore by copying the old pointer value back — no field is ever mutated through it, so an old clone is always a complete, correct undo. `rg -n 'func.*restore' internal/session` before adding it found only the 3 bespoke closures being replaced.
- design: `railWrite` struct + `errRailWriteAborted` sentinel. `applyRailChangesLocked` now draws each changed session's write ticket and captures its `prev` clone while still under `m.mu` (previously it only built snapshots); `persistAndBroadcastRail` reuses `finishWrite` for both the real writes and, on a failure partway through, the abort path for every write still queued behind it (by handing `finishWrite` a synthetic always-failing `persist` so its existing restore-and-signal logic runs) rather than writing a second, parallel rollback loop.
- design: `MarkPlanWritten` is a new `Manager` method, not a change to `SetPlan`'s signature — `SetPlan` is called directly by 9+ existing tests (`internal/session/reader_test.go`, `internal/server/reader_test.go`) with its general `(path, exists)` shape, and per the plan's "two shapes for one wire field" lesson, bending `SetPlan` to also do a compare-and-set would have been the wrong fix for a caller (`observeWrite`) that needs different semantics (commit only if `PlanPath` is *still* the path this call qualified, decided fresh under the lock, never the value the caller read outside it). `rg -n '\.SetPlan\(' internal internal/server` confirmed every other caller already holds a real, current path and keeps using `SetPlan` unchanged.
- `nextRailPos int64` field on `Manager`, seeded by `LoadAll` from `maxRailPosLocked()+1` (the old computation, now run once instead of per-`CreateSession`) and incremented under the same lock scope it's read in (a-M2's fix: "decided and advanced in one critical section"). This makes railPos allocation monotonic rather than "current max + 1" — a session created after the highest-railPos session was removed now gets a higher value than before, not a reused one. Checked against `TestCreateSession_FirstSessionRailPosIsZeroAndUnpinned`/`TestCreateSession_RailPosIsMaxOfExistingPlusOne` (exact-value assertions, still 0/1/2 for successive creates with no removals) and `TestCreateSession_RailPosAccountsForAPinnedExistingSession` (relative-`Greater` assertions) — all three still pass; `rg -n 'RailPos' internal/session/*_test.go` found no test that creates, removes the highest-railPos session, then creates again expecting a specific reused value.
- `BumpIDWatermark` wrapped in `s.db.BeginTx`: relies on `Store.Open`'s existing `SetMaxOpenConns(1)` (documented there as the store's concurrency control) to guarantee no other statement — including `InsertSession`'s own transaction — can interleave with the held connection. No new store-level primitive needed.
- Kept `persistAndBroadcastRail`'s original "stop at first failure" policy rather than switching to "attempt every entry, aggregate errors" (Reconcile's `actOnReconcile` pattern) — smaller behavioural delta from the existing doc ("stops and returns the first persist error"), while still fixing the actual defect (memory left ahead of the DB for the un-persisted tail).
- Every REQ the plan's F1 unit lists is addressed: S1(widened)/S2/b-M1, a-C1, a-M2, a-M3, a-note-3 (truncate half) — see table above and the interleavings below.
- No deviation from the plan; no doc-delta (protocol/spec unchanged, this is an internal correctness fix with no wire-visible behaviour change apart from `RailPos` values no longer being reused after a removal, which is not a documented contract — order-sidebar's spec only promises relative ordering).

## Interleavings daemon-tests should drive

1. **Critical 1 (Model pointer mutation), deterministic, single goroutine:** create+launch a session (so it has a `Model`), take a clone via `mgr.Get(id)`/`mgr.List()`, then call `mgr.Apply(...)` with a bind-kind input carrying a *different* model id. Assert the clone taken *before* the bind still reports the *old* `Model.ID` (fails on pre-fix code, since `sess.Model.ID = *input.Model` wrote through the same pointer the clone shares).
2. **Critical 1, race-detector-driven:** N goroutines calling `Apply` with alternating bind-kind inputs (different models) concurrently with N goroutines calling `List()`/`Get()` and reading `.Model.ID`, under `-race`. Pre-fix: a real `DATA RACE` on the `Model.ID` field write vs. the unsynchronized read through a `Clone()`-shared pointer. Post-fix: clean, since a changed `Model` is always a fresh pointer.
3. **a-M2 (CreateSession railPos), goroutines:** launch two `CreateSession` calls concurrently for different directories (matching `TestLauncher_ConcurrentLaunchesForTheSameDirectoryProduceTwoDistinctRows`'s existing shape at the `Manager` level, not just the launcher's), assert the two sessions get distinct `RailPos` every run (loop N times to make a flaky pre-fix failure visible) — pre-fix, both can read the same `nextRailPos`-equivalent max before either registers.
4. **a-M3 (watermark race):** two goroutines, one calling `store.InsertSession` and one calling `store.BumpIDWatermark` with a `minID` lower than what `InsertSession` is about to commit, run concurrently in a loop; assert the persisted watermark (`KVGet("session.id_watermark")`) never ends up lower than the highest id `InsertSession` actually allocated across the run.
5. **b-M1/a-S2 (`MarkPlanWritten` CAS), deterministic:** bind a session to `claude-1`; get it to `PlanPath=P, PlanExists=false` (e.g. via `SetPlan(id, "claude-1", P, false)`); call `ApplyPlanScan(id, "claude-1", P2)` to commit `PlanPath=P2` (use a temp file for `P2` so `PlanExists` derives true); then call `MarkPlanWritten(id, "claude-1", P)` (the stale path `observeWrite` would have qualified before the scan landed) and assert `changed=false` and `PlanPath` is still `P2` — this is exactly the finding's reproduction, and it fails (silently overwrites `PlanPath` back to `P`) if `observeWrite`/`SetPlan`'s old call shape is used instead. Also cover the true-flip case: `MarkPlanWritten(id, "claude-1", P2)` when `PlanExists` is still false → `changed=true`, `PlanExists=true`, one broadcast.
6. **S1 (persist-failure policy uniformity):** using the existing `st.Close()` seam (`TestMarkEnded_APersistFailureLeavesTheInMemorySessionAliveMatchingTheDB`'s pattern), close the store before calling each of `Apply`, `ApplyStatus`, `SetTitle`, `MarkSeen`, `SetTranscript`, `SetPlan`, `MarkPlanWritten`, `ApplyPlanScan`, `RepairOwnedSession`, `RecordResume`, and assert the in-memory session is byte-identical to its pre-call clone afterward (rollback occurred) for each. Also drive `SetOrder`/`SetPinned` with 3+ affected sessions and a closed store: assert *none* of the affected sessions differ from their pre-call state (not just the one whose persist happened to run first) and none was broadcast.
7. **S1 (ordering primitive, unit-level on `nextWriteTurnLocked`/`finishWrite` directly, white-box):** since real DB-call timing can't be forced deterministically, draw tickets `t1, t2, t3` for the same id (three sequential `nextWriteTurnLocked` calls), then run their `finishWrite` calls from goroutines started in *reverse* order (`t3`'s goroutine first) with each `persist` appending its id to a shared, mutex-guarded slice; assert the slice ends up `[1, 2, 3]` regardless of goroutine start order or injected `persist` delays.

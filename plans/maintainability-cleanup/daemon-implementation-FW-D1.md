## Decisions

- deviation: `finishWrite`'s signature is unchanged (still `persist func() error`, single `error` return, `sess *Session` including a literal `nil` in the white-box ticket-ordering test) because `manager_writeorder_test.go`'s `TestWriteTurns_FinishWriteOrdersPersistsByTicketNotGoroutineStartOrder` calls it directly with exactly that shape and I may not edit test files. The fix for a-M1/a-M2 therefore lives entirely in what callers pass `finishWrite`, not in `finishWrite` itself: `persistWholeRow`/`wholeRowPersist`'s `persist` closures re-read live memory when invoked (turn time), and `restoreChangedFields` replaces the restore closure every setter used to pass. → ADR: pending.
- design: `persistWholeRow`/`wholeRowPersist` (writeorder.go) are the one owner for the whole-row setter tail (a-Major 3) — `rg -n 'nextWriteTurnLocked' internal/session/*.go` before the change showed 12 call sites each hand-building `row := sessionToRow(sess); snapshot := sess.Clone(); wait, done := ...; m.mu.Unlock(); persist := func() error {...}; m.finishWrite(...)`; now 9 of them (SetTitle, MarkSeen, SetTranscript, SetPlan, MarkPlanWritten, ApplyPlanScan, RecordLaunch, RecordResume, markEnded, RepairOwnedSession, reviveOwnedSession, ApplyStatus — 12 total) call `persistWholeRow` in 2-4 lines. `wholeRowPersist` is split out of `persistWholeRow` so Apply (which needs an extra byClaude restore step) and the rail batch (which needs a custom abort-the-rest-of-the-batch failure path) can reuse the identity-checked live-read without re-deriving it inline — reusing it in `Apply` itself is what brought `Apply`'s cyclomatic complexity back under golangci-lint's ceiling of 15 (it hit 16 with the identity check inlined; `golangci-lint run` confirmed `0 issues` after the split).
- design: `restoreChangedFields`/`restoreIfUnchanged[T comparable]` (writeorder.go) — a generic per-field compare-and-swap, not a hand-written field list per setter or a whole-struct copy. `rg -n 'func.*restore' internal/session` before adding it found only `cloneRestore` (the whole-struct version being replaced) and the setter-specific `restore` closures inline in `apply.go`/`manager_rail.go`. A per-field list was considered for `Apply` specifically (it mutates a well-known, enumerable set of state-machine fields) but rejected: `applyInput`'s per-`Kind` mutation set isn't uniform (e.g. `Unread` only changes on `KindTurnClosed`), so a hand-written list would need to replicate that conditional logic to avoid reverting a field `Apply` never touched this call and stomping a legitimate concurrent write to it — exactly the bug this fix removes. Comparing `prev`/`post` (both clones taken atomically under one lock scope) sidesteps that: it needs no knowledge of which kind did what. Verified this is a strict refinement of the old whole-struct restore with no queued write racing (every field still reads as `post`, so every branch fires) via `go test -race -count=1 ./internal/session/...`, which still passes `TestPersistFailure_RollsBackEveryMutationUniformly` (single-writer case) unmodified.
- design: `currentPromptID`/`closedPromptIDs` (Apply's in-memory-only guard fields, never part of `SessionRow`) are included in `restoreChangedFields` even though they don't affect DB consistency. First attempt excluded them (no DB-consistency reason to restore them) — `go test -race -count=1 ./internal/session/...` then failed `TestPersistFailure_RollsBackEveryMutationUniformly/Apply` (`manager_writeorder_test.go:341`, a frozen test I may not edit), which asserts full byte-identity including unexported fields via `assert.Equal`. Included them; the suite passes. `closedPromptIDs` is a `[]string` (not `comparable`), so it can't go through `restoreIfUnchanged`'s generic — it gets its own `slices.Equal`-gated branch.
- design: `Manager.removeSessionRecord`'s `announced bool` parameter (was `notify`) governs both the OnRemoved callback *and* the store/memory ordering, with the rationale for why one flag covers both written into its doc — an announced session (Remove) needs the store delete to succeed before memory drops (so a failed delete never makes a session live clients believe exists vanish from `List()`); a never-announced one (DeleteSession's launch rollback, Reconcile's startup sweep) needs the opposite: memory drops regardless of the delete's outcome, because no client has ever seen a sessionUpsert for it and a stale row in `m.sessions` would otherwise surface in the next snapshot purely because a DB error happened to land. The store error is still returned to the caller in both cases (memory dropping doesn't swallow it) — a real DB failure stays worth logging even once the visibility hazard is closed. Verified with a scratch reproduction (drew an in-flight ticket manually, launched `removeSessionRecord` in a goroutine, confirmed it blocked until the in-flight ticket's `done()` fired, then confirmed a write ticketed behind the removal got `ErrUnknownSession` and never broadcast or resurrected the row) — deleted before this log was written, per the no-report-files convention; the failing→passing sequence is reported here as the evidence, not a file left behind.
- design: `Store.log zerolog.Logger` + `SetLogger`, not a required `Logger` parameter on `Open`. `rg -n 'store\.Open\(' --include=*.go .` found 22 call sites, 21 of them two-arg test calls I may not edit; adding a required third parameter would break every one of them. A zero-value `zerolog.Logger{}` is a genuine no-op (verified against `github.com/rs/zerolog@v1.35.1`'s source: `Logger.disabled()` returns `true` whenever `l.w == nil`, which is exactly the zero value's writer, so `should()` short-circuits to `false` and every level method becomes a no-op before touching a nil `LevelWriter`) — so an untouched `Store` from any of those 21 call sites behaves exactly as before (silently drops the new warning), and only `cmd/musterd/main.go`'s one call to `SetLogger` makes it visible.
- design: `scanSession` is now a `*Store` method rather than staying a package function taking the logger as a parameter — it already needed `*Store` for nothing before, but every other scan/decode helper in the file (`decodeRowTime`/`decodeRowTimePtr`) needs `s.log`, and threading a `zerolog.Logger` positionally through `scanSession`'s two callers (`GetSession`, `ListSessions`) for a value they already have on `s` would be one more parameter for no reason.
- Every REQ this fix wave's scope names is addressed above: a-M1, a-M2, a-M3 (`persistAndFinishLocked` relocated to `writeorder.go` as `persistWholeRow`), a-M4 (`collectLocked`→`collectSessions`), a-M5 (`SetPlan`'s doc), a-Minor 1 (finding-tag/history sweep across `manager.go`, `actions.go`, `liveness.go`, `row.go`, `store/store.go`, `store/migrate.go`, `store/repo.go`), a-Minor 2 (`manager.go`'s railPos/`removeFromMemory` docs, `actions.go`'s `ShellNames` doc, `store/session.go`'s `RailPos` doc), a-Minor 3 (`keyedlock.Forget`), a-Minor 4 (`sessionTmuxName` deleted), a-Minor 5 (`MarkSeen` moved), a-Minor 6 (`sessionSnapshot`→`sessionRef`), a-Minor 7 (`Config`'s `OnUpsert`/`OnRemoved`/`Watcher` doc), item (a)/(b)/(c) from the team lead's behaviour findings.
- Not done, deliberately: a-Minor 8 (test comment tags, `fakeKiller` naming) is a test-file change I may not make — see Handoff. Note 7 (the `keyedlock`/`boundedwait` package-doc reasoning) is out of this wave's requested scope (Majors 1-5 + Minors only) and touches `internal/boundedwait`, which isn't mine to edit — left as-is so the two sibling leaf packages' docs don't diverge.

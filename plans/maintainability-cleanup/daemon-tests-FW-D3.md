## Test 1: `TestUpdateManager_StopNeverRacesAnApplyThatHasRegistered`

**Interleaving forced without a sleep**: 24 goroutines per trial (200 trials) spin reading `m.applyInFlight` under `m.mu` — the same lock `RequestApply`'s critical section holds — and the instant one observes it flip `true`, immediately calls the real `m.Stop`. This maximizes the chance that at least one lands its own `mu.Lock()` in the pre-fix gap between `RequestApply`'s `mu.Unlock()` and its (then-external) `applyWG.Add(1)`, on a trial where the scheduler's genuine multi-core parallelism cooperates — there is no I/O boundary inside that two-line gap to gate with a channel instead.

**Correctness signal, not timing-to-force-the-race**: every trial's apply is held forever in a custom `blockForeverRoundTripper` that ignores the request's context entirely (unlike a real `*http.Transport`, which the existing `TestUpdateManager_StopCancelsAndBoundedWaitsForInFlightApply` relies on to make cancellation unblock a real request quickly — the opposite of what this test needs). A `Stop` that genuinely waited on `applyWG` must run out its own bounded deadline (150ms) before returning; a `Stop` that instead read a zero counter returns almost immediately. The assertion (`elapsed >= stopTimeout/2`) leaves a two-orders-of-magnitude margin, so it needs no fine-grained timing despite real wall-clock measurement being the final check.

## Test 4: `prefs_concurrency_test.go`'s broadcast assertion (review.work.md item, not new)

`TestHandlePutPrefs_ConcurrentPUTsAllReachTheBroadcastToo` previously read and discarded both broadcast frames, asserting only the final persisted state. Since `handlePutPrefs`' fix serialises load→persist→broadcast under one lock and a client's outbox is FIFO, the *second* frame this client receives is provably the one whose PUT loaded after the other's persist — it must carry both fields. Rewrote the drain into two `readJSON[prefsWire]` calls and asserted: the second frame has `View=="tiles"` and `Density=="3x2"` (both PUTs' fields); the first frame has exactly one of `{View:"tiles",Density:"2x2"}` or `{View:"focus",Density:"3x2"}` (its own field against the other's still-default value, matching `defaultView`/`defaultDensity` in `prefs.go`). Ran 5× under `-race` to confirm it holds regardless of which PUT the scheduler runs first (both outcomes are permitted by the assertion; the invariant checked doesn't depend on which).

Also removed this file's review-cycle citations (`review.maintainability.b-server.md`, `Critical 1 (F2)`, `daemon-tests-F2.md`) per the team lead's instruction, restating each comment's rationale directly instead (docs/conventions.md § Comments: don't narrate history).

## Notes on the reconstruction method

Per the team lead's brief, whole-file `git show HEAD:<path>` swaps were used only for the three files confirmed (via `grep -l <basename> daemon-implementation-FW-D1.md daemon-implementation-FW-D2.md` plus a successful `go build ./...` against each swap) to be untouched by FW-D1/FW-D2: `terminal.go`, `sessions.go`, `respond.go`, `issue.go`. For `updatemanager.go` (which FW-D2 did mechanically touch — the `CheckNewer` 4-value-return call), the whole-file swap was rejected in favour of hand-reverting only the one functionally-relevant hunk (`applyWG.Add(1)`'s position), leaving FW-D2's unrelated edit in place. Every swap was made in the real working file, tested, then restored from a scratchpad copy with a `diff` confirming byte-identical restoration before moving to the next file — never left mid-swap between edits.
